# Процесс выпуска FMT-exocortex-template

> Кто, когда и как бампает версию шаблона. Цель: внятный критерий «готово к выпуску»
> вместо устного соглашения. Источник: WP-347 Ф3, 22 мая 2026.
> **Выпуск по решению Выпускающего** (WP-529 Ф251, 10.11.2026) — см. «Выпуск через кандидата» ниже. Недельный авто-бамп (WP-5, 20.07.2026) отменён 03.11.2026.
> **Выпуск с ветки выпуска без остановки `main`** (WP-529 Ф268, 24.11.2026): метка — на проверенном кандидате, слияние в `main` — после выхода.

## Что означает «выпуск»

`update.sh` по умолчанию работает через канал `release`: обновление закрепляется
на последнем опубликованном GitHub Release (тег; при наличии Python тег дополнительно
разрешается в commit SHA). Коммит в `main` доходит до пользователей только после
публикации следующего релиза. Если release определить не удалось, обновление
останавливается (fail-closed) — автоматического перехода на `main` нет.
Канал `main` (`IWE_UPDATE_CHANNEL=main`) — движущаяся ветка для авторского workflow.

**Версия** в `update-manifest.json["version"]` отображается при запуске `bash update.sh`
как «Обновления экзокортекса (vX.Y.Z)», скачивается при `--check` из remote-манифеста для
сравнения с локальной и сравнивается при обновлении, если у установленной копии и релиза нет
общего коммита (форк с переписанной историей): релиз старше установленной версии считается
откатом и требует явного подтверждения (`--yes` его не применяет, без `--yes` нужно ввести
`ROLLBACK`). Формат — только цифры `X.Y.Z` (до 9 цифр в каждой части), как проверяет
`version_compare` в `update.sh`; иначе откат определить нельзя, и `--yes` останавливается.
Бамп версии = сигнал «этот набор изменений стабилизирован, пора обновляться».

## Выпуск через кандидата (release-candidate.yml, release.yml)

Недельный выпуск по расписанию отменён 03.11.2026: в выпуск входит только то,
что отобрал и проверил Выпускающий. Расписания нет, все шаги запускаются вручную
(Actions → **Release Candidate** / **Release** → Run workflow).

**Основная ветка не останавливается** (WP-529 Ф268, решение Выпускающего 24.11.2026):
`main` принимает правки и во время проверки выпуска. Метка выпуска `vX.Y.Z` ставится
на проверенного кандидата на ветке `release/vX.Y.Z`, а запрос «ветка выпуска → `main`»
вливается **после** выхода. Порядок для людей — раздел «Выпуск без остановки основной
ветки» в [`method/pipeline.md` DS-iwe-releases](https://github.com/MimEcoSys/DS-iwe-releases/blob/main/method/pipeline.md).

**Условие включения.** До первого выпуска по этому порядку владелец ставит на GitHub
защиту веток `release/*`: обязательная проверка `Validate Template` (с `release-receipt`),
запрет перезаписи истории (force push) и удаления. Без неё новый порядок не включается:
метка ставится на коммит ветки выпуска, и защищать его должна та же защита, что и `main`.

1. **Режем.** Выпускающий называет коммит основной ветки — снимок. Запуск с
   `mode=cut`, `snapshot_sha=<полный SHA>`, `release_type=patch|minor`. Workflow
   проверяет, что коммит — **вершина `main` сейчас**, что **метка прошлого выпуска
   (наибольшая `vA.B.C`) уже есть в `main`** — его запрос на слияние влит; иначе номер
   версии и `[Unreleased]` в `main` устарели и нарезка откажет, — и что `[Unreleased]`
   на снимке не пуст. Затем поднимает версию, переносит заметки в новый раздел CHANGELOG,
   обновляет значок и манифест, создаёт ветку `release/vX.Y.Z` и сразу открывает PR
   `release/vX.Y.Z → main`. Метку кандидата «режем» не ставит. Ветка с такой версией уже
   есть — отказ.
2. **Поля и отбор.** На ветке выпуска Разработчик дописывает четыре поля
   передачи всем записям раздела версии (см. «Поля записи» ниже), Выпускающий
   снимает отложенное откатом (`git revert`) — на ветке выпуска, не в `main`.
   Исправление, найденное проверкой, тоже идёт на ветку выпуска. **Правки `main` в
   выпуск сами не идут**: кандидат и его проверка не сбрасываются. Если исправление
   уже есть в `main`, Выпускающий решает: перенести его на ветку выпуска (с записью в
   разделе версии) или оставить до следующего выпуска. Влить `main` в ветку выпуска
   целиком — тоже допустимо, но это новый кандидат и все строки проверки заново.
3. **Кандидат.** После каждого изменения ветки выпуска — запуск с
   `mode=next-rc`, `version=X.Y.Z` (запускать на ветке выпуска:
   `gh workflow run release-candidate.yml --ref release/vX.Y.Z -f mode=next-rc -f version=X.Y.Z`).
   `scripts/check-release-branch-base.sh` проверяет, что вершина ветки та, что
   проверялась, что ветка нарезана от `main` и содержит прошлую метку выпуска; сдвиг
   `main` после нарезки только сообщается, не отказ. Затем проверяются поля всех записей
   раздела версии (`scripts/check-changelog-fields.py`): хотя бы у одной нет —
   метки нет. Иначе метка `vX.Y.Z-rc.N` (первая — `rc.1`) на вершине ветки и
   комментарий в PR. Если содержимое совпадает с последним кандидатом — отказ.
   `Validate Template` запускается на каждом push в `release/**`; коммит, отправленный
   программой (нарезка), проверку сам не запускает — тогда
   `gh workflow run validate-template.yml --ref release/vX.Y.Z`.
4. **Проверка.** Тестировщики ставят кандидата: `IWE_UPDATE_CHANNEL=rc bash update.sh`
   и проходят строки протокола выпуска (`releases/<X>.N/<N>/protocol.md` в
   [DS-iwe-releases](https://github.com/MimEcoSys/DS-iwe-releases)); что из строк
   блокирует выпуск, решает Выпускающий. Кроме того — **независимая атака
   (red team)** на кандидате по скиллу `iwe-platform-redteam` (метод Евгения
   Селивёрстова): проверяющий — не автор кода выпуска, вердикт навыка GO / CAUTION /
   BLOCKED (или `cannot_verify` — не пройдено) до выпуска записывается **вне дерева ветки выпуска**: комментарием в PR
   и полем `red_team` файла отметок в папке `releases/<X>.N/<N>/tests/rc.<K>/` в DS-iwe-releases (с
   меткой кандидата, к которому он относится). Запись в `docs/release-audit-log.md`
   меняет дерево ветки, и выпускать пришлось бы уже не проверенного кандидата, поэтому в
   журнал вердикт попадает отдельным PR в `main` **после** выхода. BLOCKED — не выпускать;
   существенная находка закрывается исправлением на ветке выпуска и новым кандидатом либо
   оговоркой, принятой Выпускающим. Вердикт относится к одному кандидату: новый `rc` — новый вердикт.
5. **Выпуск, затем слияние.** Выпускающий сверяет, что для последней метки `rc` в файле
   отметок папки `tests/rc.<K>/` записан вердикт `red_team` для дерева этого кандидата
   (`python3 tools/check_decisions.py --require-final --rc-tree <дерево из комментария последней метки>`
   в DS-iwe-releases), и запускает выпуск:

   ```bash
   gh workflow run release.yml --ref main -f version=X.Y.Z
   ```

   `release.yml` ставит метку `vX.Y.Z` на **коммит последнего кандидата** `vX.Y.Z-rc.N`
   ветки `release/vX.Y.Z` и создаёт GitHub Release с разделом версии из CHANGELOG этого
   коммита. Выпуск останавливается, если: кандидата для версии нет совсем (WP-529 Ф240 —
   срочный выпуск идёт тем же путём через `next-rc`); вершина ветки — не последний
   кандидат (на ветке есть непроверенные коммиты); указанный `sha` — не последний
   кандидат; дерево или версия в манифесте расходятся с кандидатом; на коммите кандидата
   нет успешного `Validate Template` (push или ручной запуск на `release/vX.Y.Z`; проверка
   запроса на слияние не засчитывается — она проверяет слияние с `main`, а не кандидата).
   Пометку «последний выпуск» (её читает `update.sh` в канале `release`) получает только
   наибольшая версия среди всех меток выпусков; для `X.Y.0` сразу создаётся напоминание
   об аудите (`post-release-audit.yml`). Затем **в тот же день** вливается PR из шага 1:
   он приносит в `main` номер версии, раздел версии CHANGELOG (выпущенные записи уходят из
   `[Unreleased]`), их поля, исправления ветки и откаты отложенного — их возврат в `main`
   отдельным действием (17а чек-листа DS-iwe-releases). PR, созданный через `GITHUB_TOKEN`,
   ожидает разрешения на запуск проверок: владелец выбирает **Approve workflows to run** и
   дожидается успешного `Validate Template` с `release-receipt`. Конфликты с правками
   `main` Разработчик сводит в этом PR, не теряя ни правку `main`, ни исправление ветки.
   **Записи, влитые в `main` после нарезки, git без конфликта переносит под заголовок
   `## [X.Y.Z]`**: на ветке выпуска заголовок версии стоит сразу под `[Unreleased]`, а эти
   записи лежат ниже него. Задача `release-merge-back` в Changelog Gate
   (`scripts/check-release-merge-back.py`) сверяет раздел `[X.Y.Z]` результата слияния с
   разделом на метке `vX.Y.Z` (до метки — на последнем `rc`) и не пускает заглушку
   «на разметке» вне `[Unreleased]`. Красная проверка называет лишние записи: влейте `main`
   в ветку выпуска, перенесите их обратно в `[Unreleased]` и отправьте ветку — только после
   зелёной проверки сливайте. Пока PR не влит, следующая нарезка откажет. Анонс подписчикам (`notify-update.yml`)
   берёт раздел версии из CHANGELOG по метке выпуска и не ждёт слияния.

**Пока не поддерживается:** исправительный выпуск старой ветки после более нового
(например, `0.42.3` после `0.43.0`). `release.yml` не даст ему пометку «последний», но
нарезка (`cut`) идёт только от вершины `main`, а условие нарезки и раздел CHANGELOG
рассчитаны на одну линию выпусков — до доработки такие выпуски не делаются.

### Поля записи (граница Разработчик → Выпускающий, WP-529 Ф252)

Запись в CHANGELOG передана в выпуск, только если под ней три подпункта с
четырьмя полями:

```
- [behavior] Что получит пользователь (WP-529 Ф252, #1510).
  - Цель: 77 · Результат: Ц77-03
  - Как проверить: bash scripts/tests/test_check_changelog_fields.py
  - Как откатить: git revert слияния #1510
```

«Цель» — номер потребности (или несколько через запятую), «Результат» — код
результата `ЦNN-NN` или `служебное — <причина>`. Changelog Gate требует поля у
записей, которые добавляет PR в `main`; накопленные до этого записи получают
поля на ветке выпуска. Проверить локально:
`python3 scripts/check-changelog-fields.py [--section X.Y.Z]`. В анонс
пользователям поля не попадают (`scripts/release-notice-build.py`).

Метку кандидата ставит `scripts/tag-release-candidate.sh` (номер — по меткам на
сервере, гонка параллельных запусков — повтор с новым номером), проверка —
`scripts/tests/test_tag_release_candidate.sh`.

Для чувствительного patch-выпуска (обновлятор, безопасность, поведение агента)
автор вручную запускает `post-release-audit.yml` с опубликованной версией:
автоматическое напоминание создаётся лишь для версий `X.Y.0`.

### Кандидат проверен, но метки выпуска нет

1. Посмотреть журнал запуска `release.yml`: причина отказа названа в ошибке шага.
2. Вершина ветки — не последний кандидат: поставить новый кандидат (`next-rc`) и
   пройти проверку заново, либо убрать с ветки непроверенные коммиты.
3. Нет успешного `Validate Template` на коммите кандидата: запустить
   `gh workflow run validate-template.yml --ref release/vX.Y.Z`, дождаться зелёного
   результата и повторить `gh workflow run release.yml --ref main -f version=X.Y.Z`.
4. Если метка `vX.Y.Z` уже есть, а GitHub Release нет, этот workflow его не
   восстановит: его шаг пропускает существующую метку. Release создаётся вручную
   (`gh release create vX.Y.Z --verify-tag --notes-file …`), пометку «последний» —
   только если это наибольшая версия.

## Критерии готовности к бампу версии

Все пункты должны быть выполнены:

- [ ] CI зелёный (`Validate Template` + все jobs)
- [ ] Нет открытых hotfix-веток (`git branch --list 'hotfix/*'` — пусто)
- [ ] CHANGELOG.md заполнен: секция `[Unreleased]` не пустая, нет «TODO» строк
- [ ] Все новые файлы добавлены в `update-manifest.json["files"]`
  (`git ls-files | python3 scripts/check-manifest-coverage.py update-manifest.json`)
- [ ] `deprecated_files` соответствует правилу (см. «Конвенция deprecated_files» ниже)
- [ ] fix-коммитов с последнего бампа ≤5 (если >5 → обязательный review нестабильности, см. секцию «Метрика стабильности»)

## Метрика стабильности

Количество fix-коммитов с момента последнего бампа версии служит прокси-метрикой стабильности кодовой базы. Порог ≤5 означает, что накопленная нестабильность ещё не критична и релиз можно проводить без дополнительного review; превышение порога требует явной оценки рисков.

```bash
# Подсчёт fix-коммитов с последнего бампа версии
# Ветка А — теги существуют (нормальный путь):
LAST_TAG=$(git tag --list 'v*' --sort=-v:refname | head -1)
if [ -n "$LAST_TAG" ]; then
  COUNT=$(git log "$LAST_TAG"..HEAD --oneline | grep -cE '^[a-f0-9]+ (fix|hotfix)(\(|: )' || true)
else
  # Ветка B — тегов нет (legacy, удалить через 2 релиза после восстановления тегов):
  LAST_MANIFEST_BUMP=$(git log -2 --format=%H -- update-manifest.json | sed -n '2p')
  if [ -z "$LAST_MANIFEST_BUMP" ]; then
    echo "ℹ️  Нет предыдущего бампа manifest — пропуск проверки fix-метрики (первый релиз)"
    exit 0
  fi
  COUNT=$(git log "$LAST_MANIFEST_BUMP"..HEAD --oneline | grep -cE '^[a-f0-9]+ (fix|hotfix)(\(|: )' || true)
fi
echo "fix-коммитов: $COUNT"
if [ "$COUNT" -gt 5 ]; then
  echo "⚠️  >5 фиксов — требуется review нестабильности перед бампом"
  exit 1
fi
```

> Fallback-ветка B удаляется через 2 релиза после восстановления нормальной тегальности.

## Шаги ручного выпуска

Для `patch` или `minor` используйте Release Candidate по шагам раздела
«Выпуск через кандидата» выше.

Для `major` или случая, когда автоматическая сборка PR не подходит:

1. Начните с актуального `origin/main` в отдельной ветке `release/vX.Y.Z`.
   Проверьте критерии готовности выше и назначьте версию явно.
2. Обновите `update-manifest.json["version"]`, перенесите `[Unreleased]` в
   раздел `[X.Y.Z]` через `scripts/changelog-flush.sh --version X.Y.Z`,
   синхронизируйте значок (`scripts/sync-version-badge.sh --fix`) и пересоберите
   манифест (`generate-manifest.sh`).
3. Отправьте ветку, откройте PR `release/vX.Y.Z → main` и дальше идите шагами 3–5
   раздела «Выпуск через кандидата»: кандидат `next-rc`, проверка, выпуск `release.yml`
   с ветки, слияние PR после выхода (WP-529 Ф268).

## Владелец выпуска

Автор шаблона (режим `author_mode: true` в `params.yaml`). Выпуск — синхронный шаг,
не может быть делегирован агентам без явного разрешения. Периодичность: по накоплению
изменений, ориентир ~1 раз в неделю при наличии значимых изменений.

Сигнал к выпуску: ≥1 фич или ≥3 фикса в `[Unreleased]`.

## Конвенция `deprecated_files`

Запись в `deprecated_files` означает: **файл УЖЕ удалён из репо или уже не используется**.
Это НЕ «планируем удалить» или «скоро мигрируем».

**Правило:**

1. Удаляешь файл из репо → в том же коммите добавляешь его в `deprecated_files`.
2. Вручную проверить что ни один скрипт/хук в репо не ссылается на этот путь:
   ```bash
   grep -r "path/to/deprecated-file" . --include="*.sh" --include="*.md" --include="*.json"
   ```
   Detector 10 в `integration-contract-validator.sh` ловит этот случай для
   `roles/strategist/prompts/` — но только для этого подмножества файлов.
   Для всех остальных deprecated-файлов ручная проверка обязательна.
3. Использовать `deprecated_files` как TODO-трекер («скоро уберём») — запрещено:
   после `update.sh` пользователь не получит новый файл, но и старый уже удалён из доставки.

**Почему важно:** если `deprecated_files` содержит файл, который runner ещё использует,
после `update.sh` runner упадёт с «файл не найден» (прецедент: `af3b15c`, роли стратегиста,
22 мая 2026).

## Чеклист при добавлении нового файла в FMT

При каждом `git add <new-file>` убедиться:

1. Файл добавлен в `update-manifest.json["files"]` (иначе пользователи не получат его).
   CI-проверка: `git ls-files | python3 scripts/check-manifest-coverage.py update-manifest.json`.
2. Если файл намеренно НЕ предназначен для доставки — добавить в `excluded_paths` или в
   один из исключённых каталогов (`.github/`, `setup/`, `seed/`, `extensions/`, `templates/`).
3. Если скрипт `.sh` — запустить `bash scripts/validate-fmt-scripts.sh scripts/` для проверки
   хардкодов и небезопасной арифметики под `set -e`.

## Полное git-зеркало шаблона с собственным CI — НЕ поддерживается (issue #850)

Полный `git clone`/fork этого репозитория (а не установка через `setup.sh` +
`update.sh`) получает `.github/workflows/*`, включая `validate-template.yml`,
вместе со ВСЕМ содержимым репозитория на момент клонирования — в том числе
файлы из `excluded_paths` (например `setup/smoke-test-fresh-install.sh`),
которые задуманы как внутренние dev/CI-файлы канона, а не часть доставки.

Если такое зеркало затем обновляется через `update.sh --yes` (а не через
`git pull` из upstream) — `update.sh` держит в актуальном состоянии только
файлы из `files`/делегированные каталоги; `excluded_paths`-файлы, однажды
склонированные, дальше не обновляются вообще. Workflow-файлы, ссылающиеся на
`excluded_paths`-тесты (`validate-template.yml` вызывает
`smoke-test-fresh-install.sh`), продолжают запускаться в таком зеркале на
`push`, но со временем сверяют актуальный workflow против устаревшей копии
теста — падение в этом сценарии не значит, что доставка сломана.

**Эта конфигурация не поддерживается.** Результаты `validate-template.yml` в
таком зеркале не показательны; сверяйте против прогона на каноне
(`TserenTserenov/FMT-exocortex-template`) на том же коммите/версии, прежде
чем считать различие реальным дефектом.
