# Процесс выпуска FMT-exocortex-template

> Кто, когда и как бампает версию шаблона. Цель: внятный критерий «готово к выпуску»
> вместо устного соглашения. Источник: WP-347 Ф3, 22 мая 2026.
> **Еженедельный авто-бамп** добавлен WP-5 (20 июля 2026) — см. «Регулярный выпуск» ниже.

## Что означает «выпуск»

`update.sh` по умолчанию работает через канал `release`: обновление закрепляется
на последнем опубликованном GitHub Release (тег; при наличии Python тег дополнительно
разрешается в commit SHA). Коммит в `main` доходит до пользователей только после
публикации следующего релиза. Если release определить не удалось, обновление
останавливается (fail-closed) — автоматического перехода на `main` нет.
Канал `main` (`IWE_UPDATE_CHANNEL=main`) — движущаяся ветка для авторского workflow.

**Версия** в `update-manifest.json["version"]` отображается при запуске `bash update.sh`
как «Обновления экзокортекса (vX.Y.Z)», скачивается при `--check` из remote-манифеста для
сравнения с локальной и сравнивается при обновлении, если у установленной копии и релиза нет
общего коммита (форк с переписанной историей): релиз старше установленной версии считается
откатом и требует явного подтверждения (`--yes` его не применяет, без `--yes` нужно ввести
`ROLLBACK`). Формат — только цифры `X.Y.Z` (до 9 цифр в каждой части), как проверяет
`version_compare` в `update.sh`; иначе откат определить нельзя, и `--yes` останавливается.
Бамп версии = сигнал «этот набор изменений стабилизирован, пора обновляться».

## Регулярный выпуск (weekly-release.yml)

До WP-5 (20 июля 2026) бамп версии был только ручным — паузы между выпусками доходили
до 2-3 недель, хотя коммиты в CHANGELOG «Unreleased» шли почти ежедневно. Причина —
уведомление пользователям в боте генерируется как пересказ CHANGELOG и висит без выпуска
до тех пор, пока кто-то не подведёт черту вручную.

**`.github/workflows/weekly-release.yml`** по расписанию (воскресенье 20:00 UTC)
проверяет `[Unreleased]` в CHANGELOG.md. Если там есть изменения, workflow
увеличивает patch-версию (`X.Y.Z` → `X.Y.(Z+1)`), переносит заметки в новый
раздел, пересобирает манифест и открывает PR из ветки `release/vX.Y.Z`.
При ручном запуске этого workflow автор явно выбирает `release_type`:
`patch` или `minor` (`0.Y.Z` → `0.(Y+1).0`). Тип выпуска не определяется по
сообщениям коммитов; major-бамп остаётся ручной работой.

Workflow явно запускает `Validate Template` на релизной ветке, чтобы
обязательная проверка `release-receipt` появилась у PR, созданного через
`GITHUB_TOKEN`. Автор проверяет и сливает PR. Проверка на итоговом коммите
`main` затем запускает `release.yml`; только после её успеха появляются тег
и GitHub Release. Без слияния PR новая версия пользователям не доставляется.

Для чувствительного patch-выпуска (обновлятор, безопасность, поведение агента)
автор вручную запускает `post-release-audit.yml` с опубликованной версией:
автоматическое напоминание создаётся лишь для версий `X.Y.0`.

### Слит релизный PR, но нет тега

1. Найти коммит слияния релизного PR и убедиться, что именно он находится в
   `main`. Сверить на этом коммите версию в `update-manifest.json`, раздел
   CHANGELOG и версионный значок README. Не запускать повторный бамп.
2. Посмотреть `Validate Template` **для этого коммита**. Если проверка
   не прошла из-за несвежего манифеста или значка, исправить их в новом PR
   (`bash scripts/sync-version-badge.sh --fix`, `bash generate-manifest.sh`),
   слить после проверок и дождаться зелёной проверки итогового коммита.
3. Если итоговая проверка зелёная, а `release.yml` не создал тег, вручную
   запустить `release.yml` с **явными** `version` и `sha` проверенного коммита:

   ```bash
   gh workflow run release.yml --ref main -f version="<X.Y.Z>" -f sha="<полный SHA проверенного коммита>"
   ```

   Ручной запуск обходит автоматическую связку с проверкой. Перед ним
   обязательно сверить зелёный `Validate Template` именно для указанного SHA
   и отсутствие тега `vX.Y.Z`; затем убедиться, что тег указывает на этот SHA,
   а GitHub Release опубликован. Если тег уже есть, но Release отсутствует,
   этот workflow его не восстановит: его шаг пропускает существующий тег.

## Критерии готовности к бампу версии

Все пункты должны быть выполнены:

- [ ] CI зелёный (`Validate Template` + все jobs)
- [ ] Нет открытых hotfix-веток (`git branch --list 'hotfix/*'` — пусто)
- [ ] CHANGELOG.md заполнен: секция `[Unreleased]` не пустая, нет «TODO» строк
- [ ] Все новые файлы добавлены в `update-manifest.json["files"]`
  (`git ls-files | python3 scripts/check-manifest-coverage.py update-manifest.json`)
- [ ] `deprecated_files` соответствует правилу (см. «Конвенция deprecated_files» ниже)
- [ ] fix-коммитов с последнего бампа ≤5 (если >5 → обязательный review нестабильности, см. секцию «Метрика стабильности»)

## Метрика стабильности

Количество fix-коммитов с момента последнего бампа версии служит прокси-метрикой стабильности кодовой базы. Порог ≤5 означает, что накопленная нестабильность ещё не критична и релиз можно проводить без дополнительного review; превышение порога требует явной оценки рисков.

```bash
# Подсчёт fix-коммитов с последнего бампа версии
# Ветка А — теги существуют (нормальный путь):
LAST_TAG=$(git tag --list 'v*' --sort=-v:refname | head -1)
if [ -n "$LAST_TAG" ]; then
  COUNT=$(git log "$LAST_TAG"..HEAD --oneline | grep -cE '^[a-f0-9]+ (fix|hotfix)(\(|: )' || true)
else
  # Ветка B — тегов нет (legacy, удалить через 2 релиза после восстановления тегов):
  LAST_MANIFEST_BUMP=$(git log -2 --format=%H -- update-manifest.json | sed -n '2p')
  if [ -z "$LAST_MANIFEST_BUMP" ]; then
    echo "ℹ️  Нет предыдущего бампа manifest — пропуск проверки fix-метрики (первый релиз)"
    exit 0
  fi
  COUNT=$(git log "$LAST_MANIFEST_BUMP"..HEAD --oneline | grep -cE '^[a-f0-9]+ (fix|hotfix)(\(|: )' || true)
fi
echo "fix-коммитов: $COUNT"
if [ "$COUNT" -gt 5 ]; then
  echo "⚠️  >5 фиксов — требуется review нестабильности перед бампом"
  exit 1
fi
```

> Fallback-ветка B удаляется через 2 релиза после восстановления нормальной тегальности.

## Шаги ручного выпуска

Для `patch` или `minor` сначала используйте ручной запуск Weekly Release с
явным `release_type`. Проверьте созданный PR и зелёный `release-receipt`, затем
слейте PR; тег и Release выпускает `release.yml` после проверки итогового
коммита `main`.

Для `major` или случая, когда автоматическая сборка PR не подходит:

1. Начните с актуального `origin/main` в отдельной ветке `release/vX.Y.Z`.
   Проверьте критерии готовности выше и назначьте версию явно.
2. Обновите `update-manifest.json["version"]`, перенесите `[Unreleased]` в
   раздел `[X.Y.Z]` через `scripts/changelog-flush.sh --version X.Y.Z`,
   синхронизируйте значок (`scripts/sync-version-badge.sh --fix`) и пересоберите
   манифест (`generate-manifest.sh`).
3. Откройте PR. Сливайте его только после проверки релизной ветки, в том числе
   `release-receipt`. Затем проверьте зелёный `Validate Template` итогового
   коммита `main`, тег и опубликованный GitHub Release.

## Владелец выпуска

Автор шаблона (режим `author_mode: true` в `params.yaml`). Выпуск — синхронный шаг,
не может быть делегирован агентам без явного разрешения. Периодичность: по накоплению
изменений, ориентир ~1 раз в неделю при наличии значимых изменений.

Сигнал к выпуску: ≥1 фич или ≥3 фикса в `[Unreleased]`.

## Конвенция `deprecated_files`

Запись в `deprecated_files` означает: **файл УЖЕ удалён из репо или уже не используется**.
Это НЕ «планируем удалить» или «скоро мигрируем».

**Правило:**

1. Удаляешь файл из репо → в том же коммите добавляешь его в `deprecated_files`.
2. Вручную проверить что ни один скрипт/хук в репо не ссылается на этот путь:
   ```bash
   grep -r "path/to/deprecated-file" . --include="*.sh" --include="*.md" --include="*.json"
   ```
   Detector 10 в `integration-contract-validator.sh` ловит этот случай для
   `roles/strategist/prompts/` — но только для этого подмножества файлов.
   Для всех остальных deprecated-файлов ручная проверка обязательна.
3. Использовать `deprecated_files` как TODO-трекер («скоро уберём») — запрещено:
   после `update.sh` пользователь не получит новый файл, но и старый уже удалён из доставки.

**Почему важно:** если `deprecated_files` содержит файл, который runner ещё использует,
после `update.sh` runner упадёт с «файл не найден» (прецедент: `af3b15c`, роли стратегиста,
22 мая 2026).

## Чеклист при добавлении нового файла в FMT

При каждом `git add <new-file>` убедиться:

1. Файл добавлен в `update-manifest.json["files"]` (иначе пользователи не получат его).
   CI-проверка: `git ls-files | python3 scripts/check-manifest-coverage.py update-manifest.json`.
2. Если файл намеренно НЕ предназначен для доставки — добавить в `excluded_paths` или в
   один из исключённых каталогов (`.github/`, `setup/`, `seed/`, `extensions/`, `templates/`).
3. Если скрипт `.sh` — запустить `bash scripts/validate-fmt-scripts.sh scripts/` для проверки
   хардкодов и небезопасной арифметики под `set -e`.

## Полное git-зеркало шаблона с собственным CI — НЕ поддерживается (issue #850)

Полный `git clone`/fork этого репозитория (а не установка через `setup.sh` +
`update.sh`) получает `.github/workflows/*`, включая `validate-template.yml`,
вместе со ВСЕМ содержимым репозитория на момент клонирования — в том числе
файлы из `excluded_paths` (например `setup/smoke-test-fresh-install.sh`),
которые задуманы как внутренние dev/CI-файлы канона, а не часть доставки.

Если такое зеркало затем обновляется через `update.sh --yes` (а не через
`git pull` из upstream) — `update.sh` держит в актуальном состоянии только
файлы из `files`/делегированные каталоги; `excluded_paths`-файлы, однажды
склонированные, дальше не обновляются вообще. Workflow-файлы, ссылающиеся на
`excluded_paths`-тесты (`validate-template.yml` вызывает
`smoke-test-fresh-install.sh`), продолжают запускаться в таком зеркале на
`push`, но со временем сверяют актуальный workflow против устаревшей копии
теста — падение в этом сценарии не значит, что доставка сломана.

**Эта конфигурация не поддерживается.** Результаты `validate-template.yml` в
таком зеркале не показательны; сверяйте против прогона на каноне
(`TserenTserenov/FMT-exocortex-template`) на том же коммите/версии, прежде
чем считать различие реальным дефектом.
