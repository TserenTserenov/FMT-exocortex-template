# ADR-004: Карта доменов данных IWE

**Статус:** Принято (методология, рекомендуемая структура)
**Дата:** 2026-08-16 (поправка 2026-08-18: домены 2.5/2.6 → `machine-dialogue`; roles→family таблица и правила `MC-slug` добавлены 2026-08-28)
**Контекст:** РП-526 (Новая структура IWE), Ф2/Ф4/Ф5/Этап 6, пир-сессии Claude+Kimi `2026-08-16-21-wp526-f4-template-transfer` и Claude+Kimi+Codex `2026-08-28-12-wp526-migration-continue`

## Контекст

Структура репозиториев внутри одного экземпляра IWE (шаблон + пользовательские репо) складывается стихийно, если её не спроектировать заранее: типы данных пользователя (профиль, события, знания, сессионные диалоги и т.д.) смешиваются с кодом, планами и машинными артефактами в одном месте, что со временем бьёт по скорости работы инструментов, безопасности (карантин персональных данных держится на конвенции, а не на структуре) и по возможности обновлять шаблон без ручного слияния конфликтов.

Эта карта — результат отдельного разбора (РП-526), прошедшего внутреннюю архитектурную оценку (профиль ЭМОГССБ, критические характеристики — Безопасность и Эволюционируемость — без вето). Она фиксирует **рекомендуемую** структуру для нового пользователя IWE, а не обязывает существующих пользователей к миграции: у каждого пользователя может быть свой путь и темп приведения своей структуры к этой карте (или отклонение от неё по собственному решению).

**Смежный документ:** [DATA-RESIDENCY.md](../DATA-RESIDENCY.md) — более ранний и более простой предшественник (WP-475, 10.07.2026), §3 которого содержит текстовую таблицу 4 типов данных (2.1-2.4) без темпа изменения, чувствительности и правил потоков. Этот ADR не заменяет и не редактирует тот документ (он держит свою собственную, уже закрытую фазовую границу) — он вводит более полную, машиночитаемую карту рядом, с явной перекрёстной ссылкой в одну сторону (отсюда → туда).

## Решение

### Карта доменов (тип × темп)

Ось темпа: **hot** (правится ежедневно/ежесессионно) · **warm** (по фазам работы, неделями) · **cold** (архив, редко или никогда).

| Домен | Темп | Роль хранилища | Обоснование |
|---|---|---|---|
| 2.1 факты о носителе (профиль, характеристики) | warm | `personal-declarative` (git) + платформенная runtime-проекция | декларация и вычисляемое значение разделены по роли, не смешиваются |
| 2.2 события/телеметрия | hot | `personal-data` (git, append-only) + платформенная БД | активный поток записи — источник наибольшего роста истории и конфликтов при смешении с планированием |
| 2.3 знания/captures | warm | вне-git память + промотированное знание (Pack) | сырые заметки и оформленное знание — разные стадии жизненного цикла, разные дома |
| 2.4 неформализуемое | — | явный карантин «не размещать» | не структура, а маркер — решение принимается отдельно, эта карта только на него ссылается |
| 2.5 диалоговые артефакты (сессионные транскрипты) | warm→cold | `machine-dialogue` (git, `MC-*`, напр. `MC-sessions`; поправка 2026-08-18 ниже) | не факт, не телеметрия и не готовое знание — сырьё для последующего извлечения знания; со временем архивируется, не удаляется |
| 2.6 карантин-диалоги (подмножество 2.5) | — | тот же дом, что 2.5, с отдельным access-контролем | данные о третьих лицах внутри диалогов требуют более строгого режима доступа, чем остальной домен 2.5 |
| runtime/state | hot | вне git (например `.iwe-runtime/`) | декларируется явно как класс дома, не переносится в git-историю |
| код/скрипты — рабочая копия | hot | рабочий репозиторий пользователя | правится в ходе любой сессии, где нужен фикс инструмента |
| код/скрипты — промотированная копия | warm | `FMT-exocortex-template/scripts/` | обновляется по решению о промоции, не ежедневно — та же логика, другая стадия |
| планы/рабочие контексты | hot | `governance-personal`, без потока телеметрии и без единого растущего файла знаний внутри | смешение планирования с активным потоком записи — источник конфликтов при закрытии сессий |

### Роли хранилищ

Поле `homes` в [DATA-DOMAINS-REGISTRY.yaml](../DATA-DOMAINS-REGISTRY.yaml) использует переносимые ролевые метки вместо имён конкретных репозиториев (имена репозиториев — личный выбор каждого пользователя, не часть шаблона). Колонка «Семья» — префикс, под которым роль физически заводится (карта репозиториев IWE, WP-526 Ф5, решение пилота 18.08 — см. поправку ниже):

| Роль | Назначение | Семья | Пример |
|---|---|---|---|
| `governance-personal` | Планирование, рабочие контексты | `DS-*` | личный стратегический репозиторий пользователя |
| `personal-data` | Активный поток событий/телеметрии (2.2), карантин вне оси | `PD-*` | отдельный append-only репозиторий или БД |
| `personal-declarative` | Устойчивые факты о пользователе (2.1) | `PD-*` | репозиторий с личными данными |
| `promoted-knowledge` | Оформленное, промотированное знание (2.3) | `PACK-*` | Pack-репозитории предметной области |
| `platform-runtime` | Вычисляемые/агрегированные представления | вне git | платформенная БД (для дистрибутива — опционально) |
| `machine-dialogue` | Сессионные диалоги с агентами (2.5/2.6) — человек не читает day-to-day | `MC-*` | репозиторий диалогов (см. поправку ниже) |

**Семантика `MC-*` (добавлено 2026-08-18, WP-526).** На старте семья содержит ровно один репозиторий — `MC-sessions`. Расширение семьи (второй и последующие `MC-*` репозитории) требует отдельного ADR, не вводится по аналогии.

**Поправка 2026-08-18 (решение пилота, WP-526 Ф5, третий заход 18.08 вечер) — домены 2.5/2.6 переехали из `governance-personal` в `machine-dialogue`.** Первоначальное решение 2026-08-16 (эта секция, коммит `f88a582`) относило сессионные диалоги к `governance-personal` (`sessions/` внутри личного стратегического репозитория). Пилот пересмотрел это два дня спустя: диалоги — не governance-контент, а машинные данные агент-для-агента, для которых заведена отдельная 5-я семья `MC-`. Таблица `homes` доменов 2.5/2.6 в [DATA-DOMAINS-REGISTRY.yaml](../DATA-DOMAINS-REGISTRY.yaml) исправлена соответственно. Прежнее значение (`governance-personal (sessions/)`) сохраняется здесь для истории решения, не как альтернатива.

### Машиночитаемый источник истины

Полная схема (12 доменов, темп, уровень чувствительности, разрешённые потоки, механизм контроля, зрелость) — в [DATA-DOMAINS-REGISTRY.yaml](../DATA-DOMAINS-REGISTRY.yaml). Эта таблица — сжатое человекочитаемое резюме, YAML остаётся источником истины при расхождении.

## Что не входит в это решение

- Миграция существующей структуры конкретного пользователя к этой карте — личное решение каждого пользователя, не требование шаблона. **Автоматического переноса нет и не планируется этим ADR**: у существующего экзокортекса с `sessions/` внутри governance-репозитория (структура до поправки 2026-08-18 выше) миграция на `machine-dialogue`/`MC-sessions` — ручная процедура, описанная в исходном контексте решения (WP-526 Ф5, Этап 3: `DS-my-strategy/inbox/WP-526/WP-526.md`), не в этом шаблоне.
- Механизм технического контроля доступа для карантина (2.4/2.6) — декларируется как необходимость, реализация вне рамок этого ADR.
- Правки в [DATA-RESIDENCY.md](../DATA-RESIDENCY.md) — документ отдельного, уже закрытого решения (WP-475); не редактируется.

## Поведение `session-guard.sh` без `MC-sessions` (29.08, найденный баг + фикс, пир-сессия с Kimi+Codex)

Свежая установка шаблона не получает `MC-sessions` автоматически (см. пункт выше — репозиторий заводится «по мере надобности», не при `setup.sh`). Это означало, что `scripts/session-guard.sh` (доставляется этим же шаблоном, source of truth — авторский `~/IWE/scripts/session-guard.sh`, синк — `template-sync.sh`) при первом же открытии сессии у нового пользователя падал с ошибкой «MC-sessions не найден» вместо штатной работы.

**Найденный попутно баг (не выдуманный риск — уже в коде):** строка, безусловно создающая директорию `MC-sessions` при каждом запуске скрипта, срабатывала до какой-либо проверки её существования — из-за этого предполагаемая защита «явная ошибка вместо тихой записи не туда» никогда не срабатывала: скрипт тихо использовал пустую, не git, только что созданную папку. Исправлено удалением этой ранней команды и переносом создания в точку реального использования.

**Итоговое поведение (`resolve_orz_sessions_dir()` в `session-guard.sh`):**
- `MC-sessions` существует и это git-репозиторий → используется штатно.
- `MC-sessions` физически отсутствует → это трактуется как немигрированная/свежая установка, используется путь `$GOV_REPO/sessions` (поведение до WP-526 Ф2), с явным `WARN` в stderr.
- `MC-sessions` существует, но НЕ является git-репозиторием, ИЛИ явно задан `IWE_SESSIONS_ROOT`, а путь недоступен — это трактуется как сломанная УЖЕ мигрированная установка, скрипт отказывает явной ошибкой, откат на `$GOV_REPO/sessions` не происходит (иначе получится второй, необнаруживаемый источник истины для того, кто уже мигрировал).

**Осознанно принятый остаточный риск:** отличить «никогда не мигрировал» от «мигрировал, но каталог `MC-sessions` куда-то делся» скрипт может только по наличию каталога — специального маркера миграции не заводили (лишняя инфраструктура ради редкого случая). Практически это означает: если у уже мигрировавшего пользователя `MC-sessions` будет удалён (вручную или сторонним процессом), скрипт молча откатится на `$GOV_REPO/sessions`, выдав только `WARN` в stderr — в автоматических запусках (cron/launchd) это предупреждение может остаться незамеченным. Признано низковероятным (локальный git-репозиторий с историей и remote не исчезает сам по себе) и принято сознательно, а не как недосмотр.
