# Защита от необратимых команд (destructive-guard)

Хук `.claude/hooks/destructive-guard.sh` проверяет текст каждого вызова Bash до выполнения и блокирует распознанные опасные формы: `git add -A`, `git push --force`, `git reset --hard`, удаляющий `git clean`, `git rm -r -f`, `DROP`/`TRUNCATE` через `psql`/`mysql`/`sqlite3`, удаление репозитория на GitHub и рекурсивное принудительное `rm`. Для `git clean` пропуск допускается только при распознанном действующем `-n`/`--dry-run`: отсутствие `-f` само по себе не доказывает безопасность при `clean.requireForce=false`. Код выхода 2 = команда заблокирована, агент видит причину. Границы распознавания перечислены ниже; хук не доказывает безопасность произвольного shell-кода.

## Как удалять каталоги

Распознанный вызов `rm` с ключами рекурсии и принуждения (`-rf`, `-r -f`, `-Rf`, `--recursive --force`, `/bin/rm`, `find -exec rm`, `xargs rm`, `bash -c "rm -rf …"`) блокируется и внутри `/tmp`. Хук также распознаёт `bash -o pipefail -c`, `bash -O extglob -c`, `bash -c --`, буквальное имя оболочки перед heredoc (`bash<<EOF`, `/bin/bash<<-EOF`, `'bash'<<'EOF'`) и имя `RM` на файловой системе без различия регистра. Для проверенных форм одиночной буквальной команды хук связывает тело heredoc с получателем, включая префиксные `<<EOF bash` и `0<<SQL psql`: текст для обычного `cat` остаётся данными, код для оболочки или SQL-клиента проверяется. Проверенные невложенные `if`, `for`, `while`, `until`, `select`, `case` тоже распознаются; это не полный разбор синтаксиса Bash. При присваивании, перенаправлении или обёртке перед `<<` тело сохраняется для проверки, если справа стоит буквальная оболочка или SQL-клиент и слева не распознана команда данных. Для буквальной оболочки или SQL-клиента тело heredoc сохраняется для проверки на любом FD: `/dev/fd/N` или цепочка перенаправлений может передать его интерпретатору. Поэтому `bash 2<<EOF` с опасным текстом может быть отклонён, хотя само по себе это перенаправление не подаёт тело в stdin; хук не доказывает итоговый граф FD. Неоднозначный заголовок может дать ложный отказ. Ветви проверяются консервативно: недостижимая ветвь с оболочкой может дать отказ. Динамическое имя команды или конструкция, собранная подстановкой, остаётся вне гарантии. Причина: цель удаления зависит от переменных, `cd`, ссылок и подстановок, которые известны только при выполнении, поэтому безопасность нельзя доказать по тексту команды (путь `/tmp/` в соседней команде когда-то освобождал удаление совсем других каталогов, issue #940).

Вместо этого та же команда с теми же ключами и целями запускается через обёртку:

```bash
.claude/bin/guarded-rm -rf "$TMPDIR/build"
```

Обёртка при выполнении вычисляет настоящий путь каждой цели (ссылки и `..` раскрыты) и удаляет только внутри корней из реестра `.claude/config/guarded-rm-roots.txt` (по умолчанию: `/tmp`, `$TMPDIR`, `.claude/worktrees` рабочего пространства). Сам корень не удаляется; путь вне корней, пустая цель, сбой реестра или нормализации дают отказ без удаления.

Свой каталог для разрешённого удаления добавляется строкой в реестр (данные, не shell). Реестр лежит в рабочем пространстве и не защищён от правки агентом, поэтому это удобство, а не граница безопасности против враждебного агента.

## Отказ в закрытую

Claude Code блокирует команду только при коде выхода 2. Поэтому любой другой выход хука (нет `jq` или `perl`, сбой `grep`, неожиданная ошибка под `set -e`) тоже превращается в блокировку с пометкой «ошибка проверки», а не в пропуск. Это правило относится к сбою проверки; нераспознанная опасная команда может завершить проверку с кодом 0.

## Обход для человека

`CC_ALLOW_DESTRUCTIVE_INPUT=1` задаётся в реальном шелле пилота, из которого запускается Claude Code (хук читает окружение своего процесса, агент не может выставить переменную сам себе). Это не разовый пропуск одной команды: пока переменная есть в окружении, хук пропускает без проверки все команды этого процесса, то есть всей сессии агента. Задавайте её только на время нужной операции и после неё перезапустите Claude Code без переменной.

## Вне гарантии

Хук видит только текст команды. Он не ловит: удаление средствами Python и других языков, `find -delete`, динамическое имя команды через alias/функцию/переменную, намеренный обход, ошибочный выбор цели внутри разрешённого дерева, гонку между проверкой и удалением внутри `guarded-rm`, серию вызовов `xargs` (это не транзакция), правку реестра корней инструментом записи файлов.

Составные shell-команды вне проверенных невложенных форм могут передать heredoc внутреннему интерпретатору без распознавания: например, `if true; then if true; then bash; fi; fi<<EOF`, вложенный `case` или `{ case x in x) bash;; esac; }<<EOF`. Возможен и консервативный ложный отказ: в `{ printf bash; cat; }<<EOF` слово `bash` является данными для `printf`, но хук может принять его за имя исполняемой команды; `&>/dev/null cat <<EOF bash` также может быть отклонён, хотя тело получает `cat`. Не считайте отсутствие отказа доказательством безопасности вложенной конструкции.

Кроме того, хук пропускает:

- `rm -r`, `rm -R` и `rm --recursive` без ключа принуждения (`-f`, `--force`). В вызове агента такое удаление так же необратимо: без терминала `rm` не спрашивает подтверждения и удаляет дерево целиком, в том числе файлы только для чтения (например, объекты `.git`).
- строку, которую выполняет `git submodule foreach '…'`: слова после `git` хук считает аргументами git и как команды не разбирает, поэтому `git submodule foreach 'rm -rf build'` проходит.
- текст скрипта, который оболочка получает через стандартный ввод из here-string (`bash <<<`, `sh -s <<<`) или из конвейера с источником вне буквального heredoc этой же команды (например, `printf '%s\\n' 'rm -rf …' | sh`). Буквальный `cat <<EOF | bash` проверяется, а произвольный источник `| sh` хук пока не связывает с исполняющей оболочкой.
- подстановку команды внутри двойных кавычек, например `echo "$(rm -rf …)"`, или в обратных кавычках. Текст `$(...)` выполняется оболочкой, хотя для текущего анализатора остаётся частью аргумента.
- подстановку внутри некавыченного heredoc для команды записи, например `cat <<EOF` с `$(rm -rf …)` в теле: оболочка выполняет подстановку до передачи текста в `cat`, а хук отбрасывает тело как данные.
- передачу тела heredoc в оболочку через подстановку процесса, например `cat <<EOF > >(bash)`: этот путь хук пока не связывает с исполняющей оболочкой.
- любые команды процесса, в окружении которого задана `CC_ALLOW_DESTRUCTIVE_INPUT=1` (см. «Обход для человека»).

Это известные ограничения #1002, а не разрешение удалять данные такими способами. Для удаления используйте `guarded-rm`; для остальных форм следуйте общему правилу согласования необратимых действий.

## Проверка

```bash
python3 .claude/hooks/tests/destructive-guard/hook_cases.py                 # проверки хука и этого описания
python3 .claude/hooks/tests/destructive-guard/long_cases.py                 # длинные команды (70 КБ)
python3 .claude/hooks/tests/destructive-guard/guarded_rm_cases.py .claude/bin/guarded-rm
bash .claude/hooks/tests/test-destructive-guard-executed-command-scope.sh
```

Наборы можно запускать после обновления платформы: `hook_cases.py` передаёт команды хуку как данные, а `guarded_rm_cases.py` проверяет удаление только во временных каталогах.
