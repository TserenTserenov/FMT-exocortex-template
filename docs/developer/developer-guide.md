# Гайд разработчика IWE

> Для разработчиков T4+ (TD1). Если вы не знаете свой tier — сначала прочитайте [путь по тирам](../LEARNING-PATH.md).

## Конвейер разработки — одной страницей

Разработка в IWE проходит через **6 станций** с инвариантом **двойного выхода** (код + зафиксированное знание):

1. **Постановка** — сырая нужда → задача (тег маршрутизации, класс верификации, критерий приёмки).
2. **Открытие** — WP Gate: роль, работа, класс, оценка, модель. Согласование с пилотом обязательно.
3. **Проектирование** — IntegrationGate/ArchGate для непростого; для тривиального — skip. **Первый вопрос: правка в платформенный файл (L1, напр. `day-close.sh`) или в `extensions/` (L3)?** Платформенные изменения требуют согласования — см. [CONTRIBUTING.md](../../CONTRIBUTING.md).
4. **Работа** — код + capture одновременно (не "сначала код, потом документация"). На переходе к этой станции тесты пишутся ДО кода как спецификация границы — см. [тестирование как спецификация](testing-as-spec.md). Правки кода следуют [инженерному стилю IWE](code-style.md) (P0-P12). Работа с Claude Code внутри станции — отдельная дисциплина: см. [работа с Claude в разработке](working-with-claude.md) (когда полезен/опасен, prompt-паттерны, чеклист перед merge).
5. **Проверка** — по классу верификации: closed-loop → чеклист/тесты; open-loop → peer-сессия; problem-framing → сверка с эталоном (R23/VR).
6. **Закрытие** — PR, merge ведущим разработчиком (TD1+TA4) или пилотом, обновление реестра.

**Двойной выход:** задача, после которой остался только код, считается **незакрытой**. Capture = различение, memory-файл, обновление Pack или AGENTS.md.

> **Integration/infra-задачи** (настройка окружения, внешнее API, CI/CD, деплой — не бизнес-логика): двойной выход всё равно обязателен, но capture может быть **тонким** — одно различение или одна запись в `memory/` о подводном камне, который иначе потеряется. Искусственное «различение ради галочки» не нужно; отсутствие capture = незакрытая задача.

## Что делать с первой карточкой

1. Скопируй шаблон в свою папку задач: `cp docs/developer/card-template.md <твоё-пространство>/inbox/tasks/my-card.md` (реестр и `inbox/tasks/` живут в твоём DS-пространстве, не в шаблоне).
2. Заполни frontmatter (wp, verification_class, estimate, double_exit)
3. Пройди 6 станций (карточка = вход для станции 1)
4. Закрытие: PR в репо + capture в distinctions/memory

## WP Gate — как открыть задачу

См. [CLAUDE.md §2 Pre-action Gates](../../CLAUDE.md). Обязательно объяви: роль, работу, РП, класс верификации, метод, оценку, модель. Дождись согласования пилота.

## Критерий «сделано»

- [ ] Код работает (или артефакт создан)
- [ ] Capture зафиксирован (различение / memory / Pack)
- [ ] РП закрыт в реестре (`<твоё-пространство>/docs/WP-REGISTRY.md`)
- [ ] PR влит (merge — ведущий разработчик TD1+TA4 или пилот)

## Pull Request — шаблон обязателен

При открытии Pull Request автоматически подставляется [шаблон](../../.github/PULL_REQUEST_TEMPLATE.md): ссылка на карточку, двойной выход, чеклист 6 станций, класс верификации. Заполни его честно - ревьюер по нему видит, что конвейер пройден. Пустой чеклист = PR не принимается.

## Кто принимает merge

**Только** ведущий разработчик (TD1+TA4) или пилот. Никто другой — без явного делегирования.

## Режим отказа

Если задача застряла дольше оценки (closed-loop — часы, open-loop — дни) — эскалация ведущему разработчику или пилоту. Не буксуй тихо.

## Своя идея, не поставленная задача

Если у вас есть собственная идея развития IWE, а не задача от пилота — отдельный маршрут: [процесс предложений разработчика](proposal-process.md) (предложение → согласование → материалы → работа → приёмка).

## Связь с универсальным руководством IWE

Раздел 7 «От использования к созданию» универсального руководства ([guide.system-school.ru, курс 1-3-iwe-work-and-development](https://guide.system-school.ru/universal/lr/1-3-iwe-work-and-development)) и этот гайд решают разные задачи: раздел 7 объясняет принципы созидателю, который ещё не пишет код в IWE; этот файл — конкретный конвейер для тех, кто уже пишет.

**Что попадает в раздел 7 (universal), а что остаётся здесь (developer)** — тест из двух проверок (WP-453, `pipeline-spec.md §3`), обе должны быть верны для раздела 7:

| Проверка | Вопрос | Идёт в раздел 7 | Остаётся здесь |
|----------|--------|------------------|-----------------|
| П1 | Применимо без знания конкретных файлов/команд IWE? | «Знание извлекается на каждом рубеже работы» | «Запусти `ke` скилл с аргументами» |
| П2 | Читатель уровня T3+ поймёт без прохождения этого гайда? | «Тестирование — спецификация поведения» | «Как настроить pytest fixture для MCP» |

Обе проверки верны → материал в разделе 7. Хотя бы одна не верна → материал здесь.

**Перенос контента в раздел 7 — не ручная заметка, а рабочий конвейер (WP-453).** Коммит с меткой `[guide-impact: S7.SS_N]` в изменённом файле автоматически создаёт задачу пилоту на обновление соответствующей секции — хук уже подключён (`.githooks/post-commit`). Секция «Тестирование как спецификация» (Ф1 этого гайда) уже прошла этот путь и опубликована 2026-07-02. Тексты по секциям «Стиль кода» и «Работа с Claude» (Ф2-Ф3) написаны 2026-07-24, лежат черновиком в клоне `docs` и ждут решения пилота на публикацию — конвейер до публикации не автоматический (VitePress не смотрит на `status: draft`, push публикует сразу).
