# Подключение нового ИИ-агента к IWE

> Для кого: пилот, который хочет подключить к своему форку `FMT-exocortex-template` **любого** ИИ-агента-вендора — Claude Code, Kimi Code, Codex, Hermes, ChatGPT-расширение или любой другой файловый CLI/IDE-агент, который пока не описан отдельным гайдом.
> Время: ~15-30 минут в зависимости от того, поддерживает ли агент MCP из коробки.
> Проверено живьём (28.07.2026) на 4 разных агентах одновременно (Claude, Kimi, Codex, Hermes) — координация на общих файлах без конфликтов.

Этот документ написан так, чтобы **сам агент** (не только человек) мог прочитать его и выполнить подключение самостоятельно — без предположений о том, что «уже известно» про конкретного вендора.

## Что получится

- Новый агент при открытии репозитория будет читать `AGENTS.md` и применять общие правила IWE.
- Если агент правит файлы репозитория одновременно с другими агентами — он будет координироваться с ними через общий локальный шлюз блокировок, не перезаписывая чужие правки.
- Коммиты агента будут иметь правильную атрибуцию (видно, кто из агентов что изменил).

## Шаг 1. Прочитать AGENTS.md

Файл `AGENTS.md` в корне репозитория — общий минимум правил для любого файлового агента (не специфичен под один вендор). Большинство современных CLI-агентов (Claude Code, Codex, Kimi, Cline) читают его автоматически при открытии директории — отдельная настройка не нужна.

**Проверка:** откройте репозиторий новым агентом и спросите его напрямую — «ты прочитал AGENTS.md в корне репозитория? Перечисли 3 правила из него». Если агент не может ответить — проверьте, поддерживает ли он автоматическое чтение файлов инструкций в корне репо (у части вендоров это отдельная настройка — см. документацию агента по ключевым словам «project instructions», «system prompt from file», «AGENTS.md support»).

## Шаг 2. Определить, нужна ли координация на файлах

Нужна, если одновременно с этим агентом на тех же файлах репозитория может работать другой агент (человек + Claude, или несколько CLI-агентов параллельно).

Не нужна, если агент работает соло и никогда не пересекается с другими на одних файлах — тогда можно пропустить шаги 3-4 и сразу перейти к шагу 5.

## Шаг 3. Подключить агента к локальному шлюзу блокировок

IWE использует локальный MCP-сервер (`DS-MCP/local-gateway`), который держит общий менеджер блокировок файлов. Любой агент, поддерживающий MCP (Model Context Protocol) как клиент, может подключиться к нему.

### 3.1. Проверить, поддерживает ли агент MCP-клиент

Спросите у документации агента или у него самого: «поддерживаешь ли ты подключение к внешним MCP-серверам как клиент, и можешь ли передавать переменные окружения при запуске сервера?»

Если да — у агента обычно есть подкоманда вида `<agent> mcp add` или конфигурационный файл (`config.toml`, `config.yaml`, `settings.json`), куда добавляется запись нового MCP-сервера.

### 3.2. Найти команду запуска локального шлюза

Если в `.mcp.json` вашего репозитория уже есть запись `iwe-local-gateway` (шлюз кто-то уже подключал ранее) — скопируйте `command` и `args` оттуда, это самый быстрый путь.

Если записи ещё нет — сам шлюз тоже, скорее всего, ещё не установлен (он не входит в шаблон напрямую, это отдельная зависимость с собственным жизненным циклом версий). Установите его:

```bash
bash setup/optional/setup-local-gateway.sh
```

Скрипт клонирует шлюз на закреплённую версию, соберёт его, запустит демон и выведет готовый блок `command`/`args`/`env` для вставки в `.mcp.json` — используйте его в шаге 3.3 ниже. Путь к `proxy.js` в этом блоке — `node <абсолютный-путь-к-вашему-IWE>/DS-MCP/local-gateway/dist/proxy.js`.

**Важно:** `env.IWE_AGENT_ID` в напечатанном блоке подставлен под того агента, от чьего имени запускался скрипт (или `claude-code` по умолчанию). Регистрируя **второго и последующих** агентов — замените это значение на уникальное имя каждого (см. шаг 3.3 ниже); одинаковый `IWE_AGENT_ID` у разных агентов молча ломает координацию блокировок.

### 3.3. Зарегистрировать агента с уникальным IWE_AGENT_ID

Каждый агент получает свой уникальный идентификатор через переменную окружения `IWE_AGENT_ID` — по ней локальный шлюз отличает, кто из агентов держит блокировку на файле. Идентификатор — короткое имя без пробелов (например `codex`, `hermes`, `kimikode`, `chatgpt`).

**Общий синтаксис регистрации (замените плейсхолдеры под конкретный агент):**

```
<команда-агента> mcp add iwe-local-gateway --env IWE_AGENT_ID=<уникальное-имя-агента> -- node <путь-к-proxy.js>
```

**Три реально проверенных примера** (разные агенты, разный синтаксис регистрации — общий принцип один):

```bash
# Codex (стандартный флаг --env для stdio MCP-серверов)
codex mcp add iwe-local-gateway --env IWE_AGENT_ID=codex -- node /path/to/IWE/DS-MCP/local-gateway/dist/proxy.js

# Hermes (отдельные флаги --command/--args/--env)
hermes mcp add iwe-local-gateway --command node --args /path/to/IWE/DS-MCP/local-gateway/dist/proxy.js --env IWE_AGENT_ID=hermes

# Kimi (через MCP-клиент конфиг, не CLI-подкоманду — см. docs/KIMI-SETUP.md)
```

Если у вашего агента нет ни CLI-подкоманды `mcp add`, ни конфиг-файла для MCP-клиентов — он **не поддерживает MCP как клиент**, и координацию через локальный шлюз для него настроить нельзя техническими средствами. В этом случае агент может участвовать в подключении только на уровне шага 1 (чтение AGENTS.md), без координации на файлах — сообщите об этом пользователю прямо, не изобретайте обходной путь.

### 3.4. Проверить регистрацию

```bash
<agent> mcp list
```

В выводе должна появиться запись `iwe-local-gateway`. Если агент поддерживает вызов MCP-инструментов напрямую из чата — попробуйте вызвать `gateway_status`, ответ должен вернуть `locks: []` (пустой список активных блокировок), если никто сейчас не держит файл.

## Шаг 4. Настроить строку атрибуции коммитов

Добавьте в конфигурацию агента (или используйте флаг при коммите) trailer вида:

```
Co-Authored-By: <Имя агента> <noreply@домен-вендора>
```

Например:
- `Co-Authored-By: Codex <noreply@openai.com>`
- `Co-Authored-By: Hermes <noreply@aisystant.com>`
- `Co-Authored-By: Kimi <noreply@moonshot.cn>`

Если вы не уверены в правильном домене вендора — используйте официальный домен продукта агента; при первом реальном коммите проверьте, что email не выглядит как спам-адрес и не вызывает ошибок у git-хуков репозитория.

## Шаг 5. Направить агента на скиллы IWE (опционально)

Если у агента есть свой механизм поиска дополнительных инструкций/скиллов (аналог `.claude/skills/` у Claude Code) — укажите ему путь к `.claude/skills/` вашего репозитория, аналогично тому, как это сделано для Kimi (`extra_skill_dirs` в `~/.kimi/config.toml`, см. `docs/KIMI-SETUP.md`).

Если такого механизма нет — пропустите этот шаг, это не блокирует остальную работу агента.

## Проверка подключения (smoke-тест)

Выполните на реальной небольшой задаче:

1. **Агент видит AGENTS.md** — прямой вопрос агенту, см. проверку в Шаге 1.
2. **Если координация через шлюз настроена** — `<agent> mcp list` показывает `iwe-local-gateway`.
3. **Реальная правка файла с блокировкой** (только если настраивали координацию):
   - Попросите агента вызвать `acquire_file_lock` на любом тестовом файле, внести небольшую правку, сделать коммит с правильным trailer'ом, вызвать `release_file_lock`.
   - Проверьте коммит: `git log -1 --format="%H %s%n%b"` — должен содержать `Co-Authored-By` с правильным именем и доменом.
   - Проверьте, что блокировка снята: вызов `gateway_status` должен снова показать `locks: []`.

Если что-то из этого не работает — не подключайте агента к координации на файлах, пока не разберётесь в причине; агент, коммитящий без атрибуции или не освобождающий блокировки, создаёт путаницу для остальных агентов в репозитории.

## Отличие от «оркестрации агента как напарника»

Не путайте это подключение с обёрткой-адаптером (`*-peer-adapter.sh`), где один агент headless-вызывает другого как подчинённого напарника внутри peer-сессии (один пишет, второй критикует, весь диалог управляется первым агентом). Это другой сценарий — вызывающий агент оркеструет вызываемого, а не два самостоятельных MCP-клиента координируются на равных через блокировки. Подключение из этого документа делает нового агента самостоятельным участником репозитория, а не подчинённым процессом другого агента.

## Если что-то не работает

1. Проверьте, что путь к `proxy.js` в команде регистрации абсолютный и совпадает с реальным расположением вашего клона `DS-MCP/local-gateway`.
2. Проверьте, что `IWE_AGENT_ID` в команде регистрации уникален и не совпадает с уже подключёнными агентами (`<agent> mcp list` каждого уже подключённого агента).
3. Если агент вообще не поддерживает MCP-клиента — координация на файлах для него технически невозможна, ограничьтесь Шагом 1 (AGENTS.md).
4. Посмотрите вывод `gateway_status` — зависшая блокировка (`locks` не пуст спустя долгое время) обычно означает, что предыдущий агент не вызвал `release_file_lock` после коммита.
5. Ошибка вида «connect ECONNREFUSED» или подобная при вызове инструментов шлюза обычно означает, что демон не запущен — перезапустите `bash setup/optional/setup-local-gateway.sh`, он сам проверит и поднимет демон при необходимости.

## Связанные документы

- `AGENTS.md` — общие правила для всех агентов.
- `setup/optional/setup-local-gateway.sh` — установка самого шлюза (клон, сборка, запуск демона).
- `docs/KIMI-SETUP.md` — специфика подключения Kimi Code (детальный пример шага 5).
- `docs/inter-agent-handoff.md` — передача контекста между агентами без общего шлюза.
- `memory/agent-vendor-connect-pattern.md` — краткая техническая карточка того же паттерна (справочный формат для памяти агента, не пошаговая инструкция для человека).
