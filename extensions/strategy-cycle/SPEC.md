# Контракт цикла стратегирования — спецификация

> **Назначение:** описать форму данных, которой закрытие периода (сессия/день/неделя/месяц) передаёт факты в следующее открытие, а открытие — собирает в ограниченный пакет решений для стратегической сессии. Контракт не привязан к конкретным номерам рабочих продуктов — любая инсталляция IWE реализует producer/consumer своими средствами, вплоть до «руками, по шаблону ниже».

## 1. Проблема

Закрытие периода и следующее открытие — разные моменты времени, часто разные процессы (человек за клавиатурой vs автоматика ночью). Без общего контракта каждая пара «закрытие → открытие» изобретает свой формат передачи фактов, и опыт одной инсталляции (что вошло в пакет решений, что отфильтровано, почему) не переносится на другую. Второй симптом того же разрыва: скилл `/verify-hypotheses` уже ссылается на регламент `memory/lpf-hypothesis-log.md`, которого в шаблоне физически не было до этой правки — реализация опережала спецификацию.

## 2. Что этот контракт НЕ делает

- Не предписывает конкретный механизм хранения (файл, лог, база) — только форму записи.
- Не заменяет существующий `roles/strategist/prompts/session-prep.md` — тот остаётся референсной реализацией открытия недели (читает секцию «Итоги» прямо из WeekPlan) до тех пор, пока производитель/потребитель по этому контракту не пройдёт живую приёмку на инсталляции без выделенного сервера.
- Не требует журнала гипотез или ledger-механики закрытия как обязательных компонентов — их отсутствие означает пустой вход, не ошибку (см. §5).

## 3. Событие (минимальная форма)

Любой producer (закрытие сессии/дня/недели/месяца, сверка гипотезы, обратная связь потребителя контекста) может описать факт одной записью:

```yaml
event_type: <строка>   # напр. session_closed, hypothesis_verdict, dissatisfaction_stale, guide_feedback
source: <репо или компонент-источник>
period: <дата или диапазон, к которому относится факт>
summary: <1-2 предложения человеком читаемого содержания>
requires_pilot_decision: true|false   # это факт для сведения или вопрос, требующий выбора пилота?
```

Хранение конкретных полей `event_type` — за реализацией (ledger-файл, YAML-накопитель, что угодно). Контракт фиксирует только то, что каждый producer обязан отвечать на вопрос `requires_pilot_decision` явно — это поле и есть граница между «пакет решений» и «фоновая статистика» в §4.

## 4. Пакет решений (сборка для стратегической сессии)

Consumer (открытие недели/месяца) собирает из доступных событий период а пакет с явным потолком **не более 10 позиций, требующих решения пилота** (`requires_pilot_decision: true`). Остальное — агрегированная сводка, не построчный список.

Обязательные категории пакета, если соответствующий producer в инсталляции есть (нет producer'а → категория пуста, не отсутствует из макета):

1. Фактическая загрузка и доступная ёмкость пилота за период.
2. 1-3 кандидата на изменение системного ограничения (bottleneck) периода.
3. Наступившие/спорные/просроченные гипотезы (если журнал гипотез подключён) — с альтернативными объяснениями результата, не только с «подтверждена/опровергнута».
4. Изменения реестра неудовлетворённостей: разрешённые к закрытию, новые, **стареющие без движения 8+ недель** — на стареющие обязателен принудительный выбор пилота (закрыть / переформулировать / оставить с явным триггером пересмотра), не молчаливый перенос.
5. Рабочие продукты периода, прошедшие фильтр (ограничение системы, результат периода, срок гипотезы, красная линия, новый блокер, обязательное решение пилота) — не прошедшие показываются агрегированно, не построчно.
6. Нарушения красных линий / инцидентов протокола (расхождение сценария и факта исполнения).
7. *(опционально, если в инсталляции есть бизнес/продуктовый контур)* Сигналы клиентов, рынка, денег — только пороговые (пересёк красную линию / требует решения), не сырая аналитика; конкретная бизнес-модель инсталляции не часть контракта.

Решение «не брать» по любой позиции пакета получает срок пересмотра или событие-триггер, при котором позиция автоматически возвращается — молчаливое исчезновение запрещено.

## 5. Правило деградации

Consumer обязан трактовать отсутствие producer'а (нет журнала гипотез, нет ledger'а закрытий, нет генератора персональных руководств) как **пустой вход этой категории**, не как ошибку сборки пакета. Инсталляция без ни одного producer'а получает пакет из одной категории — рабочих продуктов периода — это корректный вырожденный случай, не деградация процесса.

Это требование существует, потому что референсный ночной конвейер закрытия/открытия (если он есть в инсталляции) обычно предполагает выделенный сервер; инсталляции без сервера обязаны получать тот же пакет решений вручную или через облегчённую цепочку, без потери формы.

## 6. Открытые вопросы (до снятия статуса draft)

- **Контролируемая приёмка пробовалась 16.08.2026** (WP-518) на вердикте `H-270` из журнала гипотез: форма события (5 полей §3) покрывает всё нужное потребителям — совместимость подтверждена. Но исполняемая проба (субагент без доступа к сырому журналу, только структурированное событие + инструкция шага `06a-pool.md`) нашла **разрыв не формы, а выбора пары**: `hypothesis_verdict` описывает уже закрытую гипотезу, а `06a-pool.md` («Ставка») ожидает открытую, ещё не сверенную запись. Правильный consumer для `hypothesis_verdict` — категория 3 пакета решений §4 («наступившие/спорные/просроченные гипотезы»), не `06a-pool.md`. Приёмка пары `hypothesis_verdict → 06a-pool.md` **не пройдена**; пары `hypothesis_verdict → §4 категория 3` — не проверялась (следующий кандидат). Для проверки самого `06a-pool.md` нужен producer другого типа (открытая запись гипотезы без вердикта), которого текущий список примеров `event_type` явно не называет.
- Замена (не дополнение) `session-prep.md` на consumer по этому контракту — отдельное решение, за пределами этой поставки.
- Пересмотр контракта — не позднее первого полного цикла применения на данных реальной сверки, синхронно с ближайшей ритмичной сверкой журнала гипотез (если он подключён).

## 7. Связанные документы

- `memory/lpf-hypothesis-log.md` — регламент журнала гипотез, один из возможных producer'ов события `hypothesis_verdict`.
- `roles/strategist/prompts/strategy-session-weekly/steps/03-dissatisfactions.md`, `06a-pool.md`, `06b-budget.md` — шаги, читающие пакет решений §4 там, где он доступен.
- `extensions/strategy-cycle/scripts/validate-event.sh` (+ `test-validate-event.sh`) — механическая проверка формы события §3: пять полей, `requires_pilot_decision` строго `true|false`, `period` — дата или диапазон ISO.
