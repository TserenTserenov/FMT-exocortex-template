# Подключение агента-вендора к IWE

> **Проверено живьём:** несколько агентов-вендоров одновременно подключены к общему рабочему дереву и координируются на одних файлах через блокировки без конфликтов.

## Паттерн А — подключение нового агента-вендора

1. Агент читает `AGENTS.md` в корне рабочего дерева — общий минимум правил для файловых агентов (не Claude-специфичный CLAUDE.md).
2. Если агент правит файлы репозитория параллельно с другими — подключается к локальному шлюзу (file-lock) под своим идентификатором агента, регистрируется как самостоятельный MCP-клиент (не через Claude-оркестрируемую обёртку — см. «Отличие от peer-adapter» ниже).
3. Заводится строка атрибуции коммитов (`Co-Authored-By: <Agent> <noreply@vendor-domain>`).
4. Если у агента есть свой механизм discovery скиллов — направить на общую папку скиллов (по аналогии с уже подключёнными агентами); нет — пропустить, не блокер.

## Паттерн Б — простой выбор, кому из подключённых агентов отдать задачу

Таблица «какой агент для какого типа задачи» в проектной памяти пользователя, дополняется по мере подключения новых агентов. Пользователь (или агент перед стартом работы) сверяется с таблицей вручную — без нового инструмента.

**Триггер пересмотра таблицы:** повторяющиеся ошибочные маршрутизации задач или изменение реальных возможностей уже подключённых агентов — не разовое предпочтение.

## Отличие от peer-adapter-сценария (важно не путать)

Обёртка-адаптер (headless-вызов одного агента из-под другого, с PII-фильтром и content-guard) — это ДРУГОЙ сценарий: один агент оркеструет второго как напарника внутри диалоговой сессии (один пишет, второй критикует). Она не образец для «просто подключённого» файлового агента из паттерна А выше — там агент работает самостоятельно, не вызывается как подчинённый процесс.

## Механизм координации (техническая база паттерна А)

Локальный шлюз держит общий менеджер блокировок; каждый агент подключается через мост (stdio↔сокет), который передаёт идентификатор агента при MCP-хендшейке — идентификация агента идёт через переменную окружения, передаваемую процессу моста, отдельного API-вызова для регистрации нет.

Координация на общем файле:
1. Перед правкой → `acquire_file_lock`.
2. После коммита → `release_file_lock`.
3. Коллизия блокировки → backoff или переключиться на другой файл.
4. Архитектурное разногласие между агентами → эскалация к пользователю, не спор между собой.
