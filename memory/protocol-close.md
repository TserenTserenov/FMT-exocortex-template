# Протокол Close (ОРЗ-фрактал)

> **Четыре масштаба:** Сессия (Quick Close), День (Day Close), Неделя (Week Close), Месяц (Month Close — триггеры и инварианты в `protocol-month-close.md`).
> **Точка входа:** Вызвать Skill `run-protocol` с нужным аргументом (см. таблицу ниже).
> **Порядок чтения (WP-484.md:1953, ошибка 28.07):** если разговор перед Close шёл про конкретный РП — прочитать сегодняшние записи его WP-context ПЕРВЫМ действием, только потом открывать сам протокол. Протокол раньше контекста = причина ошибки «принял фразу пилота за отсылку к прошлому решению, не перечитав contextfile».
> **Принцип:** Quick Close = «не потерять» (inline, без TodoWrite, ~3 мин). Day/Week Close = через SKILL.md + TodoWrite (принудительное исполнение).
> **CGUS (WP-481 Ф5):** порядок шагов = порядок удержания внимания, НЕ порядок исполнения. `[[gate]]`/`[[gate:AR.NNN]]` = предусловие (блокирует); `[[narrative]]` = демонстрационный порядок (skippable). Close проверяет удовлетворённость набора gate, не линейность прохождения.
>
> **ОБЩИЙ ПРИНЦИП «Часть А / Часть Б» — для ВСЕХ ЧЕТЫРЁХ масштабов (Сессия, День, Неделя, Месяц), без исключений (WP-484, найдено 15.08 — принцип был реализован в Quick/Day/Week Close по отдельности и нигде не назван общим, из-за чего агент 15.08 не распознал его применимость к новому случаю и ошибочно предложил пилоту вручную выполнить механический шаг):** Часть А — с пилотом (все шаги, где нужно его суждение) → как только они пройдены, агент произносит хендофф-фразу «Ты свободен, дальше довожу закрытие [сессии/дня/недели/месяца] сам» → Часть Б — агент доводит ВСЮ оставшуюся механику ОДИН, без пилота (запись отчёта, коммит, архивация, метрики, верификация). Пилоту НИКОГДА не предлагается лично выполнить механический шаг закрытия (например, ввести команду в терминале сервера) — если чего-то не хватает для автоматики (нет автотриггера, нет прав, недоступен сервис), агент либо доводит это сам доступными средствами, либо честно докладывает блокер и ждёт решения, но не перекладывает исполнение на пилота. **Единственная разница между масштабами — ГДЕ внутри Части А проходит граница, не САМ факт хендоффа:** у Сессии/Дня/Недели Часть А короткая (~1-3 мин, свод + рефлексия) — почти всё остальное уже механика. У Месяца Часть А длинная и требует больше внимания пилота (фаза, калибр, ревизия проектов P1-P6, R-вопросник M1-M6, цели следующего месяца — реальные стратегические решения, агент не может принять их за пилота) — но как только эти решения приняты (после шага 9 в `month-close/SKILL.md`), должна прозвучать та же хендофф-фраза, и запись `MonthClose YYYY-MM.md` + коммит + верификация R23 (шаги 10-12) агент доводит сам, без пилота — эта фраза уже реализована как шаг 9.5 в `month-close/SKILL.md`.

## Маршрутизация

| Триггер | Аргумент | Skill |
|---------|---------|-------|
| «закрываю сессию» / «всё» / «закрывай» | `close` или `close session` | Quick Close (ниже, inline) |
| «закрываю день» / «итоги дня» | `close day` | `.claude/skills/day-close/SKILL.md` — **шаг «Мультипликатор IWE»** |
| «закрываю неделю» / «итоги недели» | `week-close` | `.claude/skills/week-close/SKILL.md` |

> **`close` без уточнения** → Quick Close (сессия) по умолчанию.

> **После закрытия дня, недели или месяца (РП-561 Ф51).** Закрытие протокола снимает только его служебный семафор. Новая задача пилота после этого требует повторного preflight и обычного открытия сессии (`protocol-open.md`, п. 2d) ДО первого коммита; в конце Day/Week/Month Close агент не продолжает работу по новым задачам под закрытым служебным семафором.


## Quick Close (сессия, inline)
<!-- section:quick-close:start -->

> **Роль:** R6 Кодировщик. **Бюджет с пилотом: ~1-2 мин** (свод + рефлексия) + **полное закрытие агент доводит один** (без пилота).
> **Принцип (DP.D.288, WP-484 31.07 — быстрое закрытие ≠ полное закрытие):** быстрое закрытие происходит быстро ДЛЯ ПИЛОТА — короткий свод того, что закоммичено, + рефлексия, не механика. Полное закрытие (WP-context, KE, MEMORY.md, R23) агент доводит сам сразу после, без пилота — результат в архиве, не в чате по умолчанию.
> «Закрывай» = push сразу без вопросов (пользователь дал согласие словом).
> **Day Close ≠ Quick Close.** Day Close самодостаточен — Quick Close внутри него не повторять.

### Раннер — условный драйвер (WP-482 Ф3+Ф5, issue #356)

> **Порядок: сначала все правки и отчёт сессии, потом первый запуск раннера (РП-484 Ф280, 31.10).** После первого `process-runner.py start quick-close` новые коммиты в сессию не добавлять: подготовленное закрытие фиксирует снимок, и следующий коммит его ломает («снимок изменился, push запрещён»). Живой случай: РП581, 31.10 — «Осталось» и отчёт сессии дописали после подготовки, вышел только аварийный `--abandon-prepared`. Нужна ещё правка → довести закрытие до конца, потом открыть новую сессию.

> **`IWE_SESSION_ID` обязателен для НЕ-Claude-агентов (WP-484, 15.09 — живой случай WP-579, Kimi).** `_env_session_id_fallback()` (`process-runner.py`) резолвит владельца карточки через `IWE_SESSION_ID`, затем `CLAUDE_CODE_SESSION_ID`. У Claude Code харнесс сам прокидывает `CLAUDE_CODE_SESSION_ID` в каждый вызов Bash — отдельный шаг не нужен. У Kimi/Hermes/Codex такого автопрокидывания нет — без явного `IWE_SESSION_ID` карточка получает `owner_session_id: null` и `session-guard.sh close` не может снять terminal proof («immutable owned snapshot»), закрытие зацикливается. Перед запуском раннера найти свой семафор точным совпадением по `slug:` (не по PID/mtime — эвристика ловит чужую параллельную сессию) среди `.iwe-runtime/sessions/<agent>-*.open` и прочитать его `session_id:`:
> ```bash
> _IWE_OWN_SEM=$(grep -l "^slug: <slug сессии>\$" .iwe-runtime/sessions/<agent>-*.open 2>/dev/null | head -1)
> _IWE_SID=$(grep '^session_id: ' "$_IWE_OWN_SEM" | head -1 | cut -d' ' -f2-)
> ```
> Передать `IWE_SESSION_ID="$_IWE_SID"` инлайн на команде ниже. Для Claude Code это не меняет поведения (тот же приоритет, то же значение по смыслу) — можно опускать, если харнесс уже гарантированно проставляет `CLAUDE_CODE_SESSION_ID`.

```bash
# #512: для установки с author_mode: false исход известен заранее — раннер
# это личный инструмент мейнтейнера (issue #306/#356), в шаблон не поставляется.
# Ветвление по params.yaml убирает файловую пере-проверку из горячего пути
# каждого закрытия; file-probe остаётся только когда флаг не читается.
AUTHOR_MODE=$(grep -E '^author_mode:' "${IWE_WORKSPACE:-$HOME/IWE}/params.yaml" 2>/dev/null | awk '{print $2}')
if [ "$AUTHOR_MODE" = "false" ]; then
  echo "Quick Close: author_mode=false — раннер не поставляется, шаги протокола вручную (штатный режим шаблона)"
else
RUNNER="${IWE_WORKSPACE:-$HOME/IWE}/${IWE_GOVERNANCE_REPO:-DS-strategy}/scripts/process-runner.py"
GRAPH="${IWE_WORKSPACE:-$HOME/IWE}/${IWE_GOVERNANCE_REPO:-DS-strategy}/scripts/processes/quick-close.yaml"
if [ -f "$RUNNER" ] && [ -f "$GRAPH" ]; then
  (cd "${IWE_WORKSPACE:-$HOME/IWE}/${IWE_GOVERNANCE_REPO:-DS-strategy}" && \
    IWE_SESSION_ID="$_IWE_SID" python3 scripts/process-runner.py start quick-close --slug <slug сессии> \
      --input '{"agent":"<agent>","wp":"<WP-N сессии или null, если сессия без своего РП>","slug":"<slug>","session_file":"<путь или null>","repos":["<repo1>", ...],"agent_suggestions":["<кандидат рефлексии 1>","<кандидат 2>"]}')
elif [ "$AUTHOR_MODE" = "true" ]; then
  echo "Quick Close: ОШИБКА — author_mode=true, а раннер или граф не найден; закрытие не начинать, доложить пилоту"
else
  echo "Quick Close: раннер не поставляется этой инсталляцией; выполнить шаги протокола вручную"
fi
fi
```

> **`agent_suggestions` (WP-520 Ф6, поручение пилота 11.08) — опционально, но заполняй:** 1-3 содержательных кандидата рефлексии — что РЕАЛЬНО происходило в сессии (инцидент, воспроизведённый урок, паттерн), не пересказ задачи и не шаблон. Хендлер вклеит их в вопрос пилоту с пометкой «Кандидаты от агента»; цифры остаются машинными, ответ пилота — только из witness (инвариант Ф56 не тронут). Поле проходит санитизацию (строки, ≤200 символов, ≤5 шт.).

Если оба файла доступны, раннер обязателен: он ведёт по шагам ниже и останавливается на каждом `pilot`/`ai`/`requires_input`; отвечать `process-runner.py next <run_id> --input '{...}'`, используя текст под каждым шагом как содержание ответа. Шаг раннера указан в скобках при каждом пункте. Если хотя бы одного файла нет, пройти те же шаги вручную, а проверки карточки раннера явно пометить `неприменимо: раннер не установлен` — это штатный режим шаблона, а не ошибка закрытия.

**Закрытие из изолированной копии (РП-484 Ф162).** Если раннер остановился на `blocked-session-release`, потому что его собственная незакоммиченная RUN-карточка мешает удалить копию, перенести ЭТУ карточку штатным вызовом из той же копии:

```bash
python3 scripts/process-runner.py relocate-card <run_id> \
  --guard-session-id <точный session_id своего семафора> \
  --actor <агент> --reason 'RUN-карточка мешает очистке своей изолированной копии'
```

Исполнить возвращённый `resume_command` в фоне, сохранив идентичность текущего рантайма и `IWE_SESSION_ID`; он содержит каталог назначения и `next <тот же run_id> --input '{}'`. Не создавать новый прогон и не переносить файл вручную. Шаг освобождения имеет отдельный предел 900 секунд: публикация и очистка могут занимать дольше общего лимита обработчиков. Это предел ожидания, не обещанное время закрытия. При длительной операции соблюдать обычный протокол коротких сообщений о ходе работы.

До первого освобождения раннер сохраняет точный guard ID в RUN-карточке. Если ответ потерян после закрытия, повторить `next` того же прогона: подтверждённый `.open.closed` признаётся без повторной публикации. Повреждённое подтверждение или несовпадение владельца оставляет блокировку; переход к поиску по одному slug запрещён. Служебная карточка в замороженном каноне сохраняется без автокоммита; завершённую карточку публиковать существующим адресным `publish-card`, не общим `git add`.

**Два пункта чеклиста раннер пока не покрывает** (нет отдельного шага в
`quick-close.yaml`) — выполнять вручную: Decision log и Docs Gate (условный).
Наличие conversational-report при переданном точном peer-контексте теперь
считает `verify-r23-mechanical`; штатная peer-finalize пока обходит этот граф,
поэтому её покрытие этим не заявляется.

## ЧАСТЬ А. Быстрое закрытие (с пилотом, ~1-2 мин)

> **DP.D.288.** Единственная цель этой части — убедиться, что работа не потеряна (закоммичена и запушена), и собрать рефлексию пилота. Никакой механики здесь не считается и не пишется — она вся в Части Б, без пилота.

### 1. Pre-commit checks → Commit + Push (шаги `precommit-checks` → `commit-push` → `commit-push-check`) [[gate:AR.005]]

**1a. Pre-commit checks (БЛОКИРУЮЩЕЕ).** `bash .claude/scripts/load-extensions.sh protocol-close checks` — exit 0 → `Read` каждый файл из вывода (alphabetic) → выполнить. Exit 1 → пропустить. **При ❌ commit запрещён** — исправить, повторить checks.

**1b. Commit + Push (БЛОКИРУЮЩЕЕ, шаг `commit-push`, вход `{"commits":[{"repo","paths","message"}, ...]}`).** `git status --short` по ВСЕМ репо, которых касалась сессия. Незафиксированные изменения → `git add <specific paths>` → commit → push. При доступном раннере использовать его хендлер и не обходить `blocked-push-failed`; в ручном режиме провал push так же блокирует переход к следующему шагу.

**Своя работа уже закоммичена и запушена, коммитить через раннер нечего (WP-484 Ф61, 05.08 — не редкий случай при инкрементальных коммитах по ходу сессии).** НЕ передавать `commits: []` без пояснения — `commit-push.sh` больше не примет это молча, но и не откажет тихо: `next` с входом `{"commits":[],"confirmed_clean_repos":["<repo1>", ...]}` — хендлер сам перепроверит `git status`/`git rev-list @{u}..HEAD` для каждого названного репо и примет как `already-there`, только если заявка подтвердилась. Ложная заявка (реально грязно или есть неотправленные коммиты) → `all_pushed: false`, `blocked-push-failed` как обычно.

**Обязательно вместе с заявкой (WP-484, пир-сессия 2026-09-11-08 с Kimi+Codex, `bug-2026-09-11-quick-close-confirmed-clean-repos-blind-to-cherry-pick-delivery.md`):** (1) поле `session` во входе — `{"commits":[],"confirmed_clean_repos":[...],"session":{"agent":"claude-code","wp":"WP-NNN","slug":"<slug сессии>"}}`, иначе хендлер не найдёт семафор и проверит ВСЮ ветку (в общем чекауте с чужими неопубликованными коммитами это отказ всегда); (2) после КАЖДОГО коммита по ходу сессии — `bash "${IWE_SCRIPTS:-$HOME/IWE/scripts}/session-guard.sh" note-commit <sha> --repo <repo> --wp WP-NNN --slug <slug>` — единственное доказательство принадлежности коммита сессии; доставка через cherry-pick (другой SHA на origin) распознаётся по patch-id только для объявленных коммитов. Без `note-commit`, но с найденным семафором хендлер работает в режиме `session_scope_inferred`: пропускает, только если ни один неопубликованный коммит ветки не трогает файлы сессии, иначе отказывает как «неоднозначный» — не как «ваш коммит».

**1c. Строка о доставке в шаблон (РП-529 Ф248, 31.10, решение пилота) · [[narrative]].** Если сессия правила файл с `delivery: managed` (frontmatter), в итоге закрытия назвать его одной строкой: «изменён managed-файл X — в шаблон попадёт на закрытии недели через список расхождений». Ничего не записывать и не вызывать `template-sync.sh`; строка — напоминание пилоту, не вход решения о доставке.

### 2. Короткий свод + рефлексия (шаги `reflection-gate` → `session-reflection-render` → `session-reflection-append` при `reflection_due: true`, WP-484 Ф56 05.08 — три reflex-шага вместо одного ai-шага) [[gate]]

**Механизация (WP-484 Ф56, пир-сессии с Codex+Kimi 05.08).** Раньше `session-reflection` был ai-шагом: раннер принимал `answer` из `--input` закрывающего агента без проверки, кто его реально написал — судья и нарушитель совпадали (3 рецидива за один день, MAJOR fault). Теперь три reflex-шага закрывают это структурно, не текстом инструкции. С раннером:

1. **`session-reflection-render`** — детерминированно считает **цифры** (длительность, коммиты, репозитории — из `gather-session-facts`/`commit-push`, не из памяти агента) и формулирует фиксированный вопрос «Что сегодня в этой сессии сработало / не сработало, что стоит запомнить?». Показать пилоту `results.session-reflection-render.digest_text` **дословно**, ничего от себя не добавлять и не переформулировать — тот же баг 31.07, что раньше подменял цифры прозой, теперь структурно невозможен, если текст не редактируется.
   - **`results.session-reflection-render.answer_prefilled` непусто (WP-484, пир-сессия с Codex 11.08)** → пилот уже назвал рефлексию в самой фразе триггера закрытия («закрывай и заливай, рефлексия — X»); `digest_text` в этом случае намеренно пуст, вопрос НЕ публиковать — сразу к шагу 3 («Ты свободен»), шаг 2 (ожидание ответа в чате) пропускается целиком, `session-reflection-append` сама подхватит `answer_prefilled` без похода в witness-файл.
   - **`results.session-reflection-render.reflection_skipped == true` (WP-484, прямое поручение пилота 11.08)** → пилот явно сказал «закрывай без рефлексии» (или синонимы «не спрашивай рефлексию», «пропусти рефлексию») — это команда пропуска, не то же самое, что пустой ответ. Вопрос про рефлексию НЕ публикуется, шаг 2 пропускается, релиз-фраза «Ты свободен, дальше довожу закрытие сам.» без придуманной строки «Записал рефлексию: ...». Если `digest_text` при этом непуст (пилот совместил «без рефлексии» с другим текстом в той же фразе, например «закрывай без рефлексии, но ещё нужно доделать Y») → показать `digest_text` пилоту как факт (не вопрос) — там сохранён остаток фразы, чтобы он не терялся молча.
2. Дождаться **настоящего** ответа пилота в чате (его пишет хук `pilot-witness-recorder.sh` установки с раннером в файл-свидетель — служебный механизм, не часть этого протокола).
3. **`session-reflection-append`** — вызвать `next`, agent-вход не содержит `answer` вообще (только `wp`/`session_file`). Хендлер сам берёт ответ из witness-файла. Три исхода: `ok` (реальный ответ найден) → к шагу 3 ниже; `autonomous_skip` (нет пилота, но есть доверенный маркер автономного запуска) → тоже к шагу 3, с текстом «нет ответа (автономный запуск)»; **`witness_unavailable`** (блок) → раннер стоит на `blocked-witness-unavailable` — это ИНФРАСТРУКТУРНЫЙ отказ (хук не сработал / файл недоступен), не «пилот промолчал»: разобраться (свежий ли `.iwe-runtime/pilot-witness/<session_id>.jsonl`, зарегистрирован ли хук) прежде чем повторять `next` на этот же шаг.

> **Правило `→ memory:`** (обязательное поле): агент явно отвечает на вопрос «нужно ли обновить MEMORY.md или memory/*.md?». Триггеры обновления: блокер снят, внешний факт изменился (чужой деплой, встреча прошла, Паша что-то починил), статус РП сменился. Если обновление нужно — сделать СЕЙЧАС, не откладывать на Day Close.

> **Поле «Следующий шаг» — единственная передача между сессиями (WP-484 Ф257, M6).** Пишет закрывающая сессия, только в карточку: отчёт и файл ОРЗ поле не дублируют. Формат: одна строка на фазу — `ФN — первое действие` (первая строка идёт после метки, следующие — продолжением ниже без пустой строки). Параллельные сессии одного РП: своя строка фазы заменяется, строки других фаз сохраняются. Запрещены стоп-фразы («продолжай по плану», «см. фазы», «продолжить») и повтор прежнего значения; при открытых фазах строка называет существующую `ФN`. Проверяет `wp-handoff-check.py`: на раннере закрытия — пятая проверка R23 `handoff_next_step`; на пути пир-сессии — `session-guard.sh close` и блок Kimi-писателя (`wp-handoff-peer-check.sh`); обе проверки пока в режиме наблюдения (предупреждают, не блокируют), порог выхода — не менее 7 дней и 5 закрытий пир-сессий, решает пилот. Фраза «Дальше» (`render-close-next.py`) берёт значение из карточки, подтверждённое проверкой, а не пересказ агента. Читатель следующей сессии — `wp-handoff-show.sh WP-N` (его вызывает `declare-intent.sh`; значение берётся со снимка origin).

> **Единственность секции (РП-541 Ф5):** заголовок `## Осталось` в карточке ровно один, точное написание без суффиксов (теневые варианты вида `## Осталось (старое)` запрещены). Вытесненный при перезаписи слой — одна строка в `## Журнал` (формат: `- YYYY-MM-DD: <итог> → <ссылка>`), не копия слоя.

### Верификация Quick Close (Haiku R23) · [[gate:AR.007]]

> Условный шаг: если `params.yaml → verify_quick_close: false` → пропустить.
> Исключения: сессия ≤15 мин, сессия-вопрос без изменений файлов.
> **Trace-satisfaction (WP-481 Ф5.1):** перед запуском R23 — `bash .claude/hooks/rule-engine.sh check-trace-satisfaction --section "Quick Close"` (без `--section` гейты Week Close и Exit Protocol из этого же файла попадают в проверку тоже — блок гарантирован, они не выполняются за 3-минутную сессию). Набор gate — строки с `[[gate…]]` внутри секции, ключи через `list-gates --section "Quick Close"`; исполненные отмечать `mark-gate <key>` по ходу Close. Verdict block → вернуться на незакрытый gate, потом R23. JSON вердикта приложить к вводу R23.
> **Механика Ф151 принадлежит handler'у.** Перед моделью раннер выполняет
> `verify-r23-mechanical`; реестр критериев читается только командой
> `${IWE_GOVERNANCE_REPO:-DS-strategy}/scripts/processes/handlers/verify-r23-mechanical.sh --list quick`. В режимах
> `shadow`/`enforce` смысловая модель не переоценивает этот результат, не пишет
> `passed` и не переносит механический пункт в смысловой вердикт. Механический
> `fail`/`notRun` в `enforce` блокирует
> путь до модели; `notApplicable` разрешён только предикатом реестра.
>
> **Без раннера** handler недоступен: один вызов Haiku идёт как в режиме `off`
> ниже (полный прежний чеклист), пункты «Механический факт раннера» помечаются
> `неприменимо: раннер не установлен`.

Режим берётся из `params.yaml → verify_r23_mechanical`:

- `shadow` — первый context-isolated вызов Haiku получает только смысловой
  чеклист ниже и возвращает `{"verdict":"pass|fail","scope":"semantic"}`.
  Затем новый, независимый вызов получает реестр `--list quick` и исходные
  артефакты, но **не** результат handler'а; возвращает строгую карту
  `{"observations":{"<check>":"pass|fail|notRun|notApplicable"}}`.
  Раннер сохраняет сравнение. Значения наблюдения не меняют `verdict`/`block`,
  но полная валидная карта обязательна для завершения shadow-прогона и зачёта
  серии 5/5.
- `enforce` — только смысловой вызов; механика уже решена раннером.
- `off` — полный откат: handler и диагностический вызов не запускаются; один
  вызов получает прежний полный чеклист и возвращает прежний ответ
  `{"verdict":"pass|fail"}` без обязательного `scope`.

Замороженная часть прежнего чеклиста только для `off` (не второй владелец
активного реестра): модель дополнительно проверяет чистоту файлов сессии,
публикацию всех её изменений, один канонический раздел `## Осталось` с восемью
bold-полями из формата выше и ровно одной строкой, начинающейся с `→ memory:`,
а также наличие
`report.md` либо `status: interrupted` у peer-сессии. Этот
rollback-снимок не используется и не развивается в `shadow`/`enforce`; новые
критерии добавляются только в реестр handler'а.

Для смыслового вызова передать: пункты 1–3 ниже, смысловые строки чеклиста
Quick Close, WP context «Осталось», `git diff --name-only`, краткое резюме
сессии и JSON trace-satisfaction. Механический результат в этот вызов не
передавать.

**Проверка факт-соответствия (не только присутствия секции):**
1. «Осталось» не шаблонная — содержит конкретику этой сессии (конкретные файлы/решения из `git diff`), не общую фразу, годную для любой сессии.
2. Если в ходе сессии агент упоминал «уже сделано» / «оказалось done» — соответствующий пункт в WP-context помечен done, не оставлен pending.
3. Расхождение (пункт помечен pending, хотя в сессии есть явное свидетельство done) → ❌, вернуть на исправление до отчёта пользователю.

Гигиену карточки, чистоту области сессии, квитанцию публикации и наличие
разговорного отчёта считает только `verify-r23-mechanical`. Терминальный статус
текущей RUN-карточки здесь не проверяется: до шага `done` он ещё не наступил.
`runner_terminated_cleanly` остаётся отдельной будущей post-terminal метрикой,
а не мнимой частью вердикта Ф151. Без раннера (скрипт или граф не установлены)
записать `runner_check: not_applicable (runner not installed)`; отсутствие
RUN-карточки тогда не является ❌.

## Мультипликатор IWE (WP-299 Ф5, шаг 6 Day Close)

> **Полная спецификация → `.claude/skills/day-close/SKILL.md` § 6.**

- **WakaTime-источник:** сводка WakaTime за дату закрытия `T="${IWE_TEMPLATE:-$HOME/IWE/FMT-exocortex-template}"; "$(bash "$T/scripts/lib/find-python3.sh" --stdlib-only)" "$T/scripts/wakatime-day-total.py" YYYY-MM-DD` (не `wakatime-cli --today`: только день вызова, пусто на части установок, issues #732, #1414) → если недоступна: Neon `domain_event WHERE event_type='coding_time'` за дату (fallback).
- **Мультипликатор** = сумма бюджетов закрытых РП за день / WakaTime (сек). Формат: `N.Nx`.
- **Эмиссия:** после вычисления — `day_close` событие в domain_event, `external_id = "day-close-YYYY-MM-DD"` (ON CONFLICT DO NOTHING — идемпотентно). Payload: `{wakatime_h, multiplier, date, session_id, source}`.
- **Pending-мультипликатор (если Day Close не успел):** Day Open шаг 1 «Вчера» — при отсутствии записи `day_close` за вчера пересчитать из Neon WakaTime (WakaTime API `summaries?start={вчера}&end={вчера}`).
