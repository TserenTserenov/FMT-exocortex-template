# Протокол Open (ОРЗ-фрактал)

> **Три масштаба:** День, Неделя и Сессия. Триггер определяет масштаб.
> **Источник:** CLAUDE.md § 2 (slim) → этот файл. **CGUS (WP-481 Ф5):** порядок шагов ниже = порядок удержания внимания, НЕ порядок исполнения. `[[gate]]`/`[[gate:AR.NNN]]` = предусловие «без этого работы нет» (блокирует); `[[narrative]]` = демонстрационный порядок (skippable). Вход «с середины» штатен, если все gate соблюдены.

## § Масштаб: День → skill `/day-open`

> **Триггер:** «открывай» / «открывай день». Полный алгоритм → `.claude/skills/day-open/SKILL.md`. **Исполнение:** пошагово через `task_tracker.create` (Host Contract DP.IWE.011 §5), каждый шаг = задача, блокирующее. Close пока вне объёма этой миграции — см. `DP.IWE.011` §9.

> **Вчерашний WakaTime (pending-мультипликатор):** в шаге 1 «Вчера» — проверить наличие `day_close` записи за вчера в Neon (`domain_event WHERE event_type='day_close' AND external_id='day-close-{вчера}'`). Если отсутствует: запросить WakaTime API `summaries?start={вчера}&end={вчера}` → пересчитать мультипликатор → дозаписать в domain_event. Причина: `--today` CLI не даёт данных за прошлый день (WP-299 Ф4 п.3).

## § Масштаб: Неделя → документы `current/WeekPlan`/`WeekState`/`WeekReport`

> **Триггер:** сессия, единственный результат которой — сам документ недели: правка направлений/РП в Плане недели в любой день недели (актуализация), стратегирование в понедельник (`skill strategy-session`), закрытие недели (`skill week-close` / `/run-protocol week-close`). **WP Gate не применяется** — предмет работы не чей-то рабочий продукт, а сам живой документ недели, по той же логике, что и масштаб «День» выше. Добавлено 17.09.2026 по решению пилота (пир-сессия с Kimi, актуализация WeekPlan W38) — до этой правки масштаб «Неделя» не был явно выведен из-под WP Gate, чем и объясняется прежняя практика подвешивать такие сессии на РП-561.
> Правка МЕХАНИКИ конвейера (шаблон, автосборка, скрипты открытия/закрытия дня/недели) — другой масштаб, не этот: туда РП-561 «Конвейер закрытие-открытие сессии-дня-недели-месяца».

## § Масштаб: Сессия (Session Open)

> **Триггер:** Любое задание (кроме Day Open/Close и масштаба «Неделя» выше — правки только документа недели уходят туда, не сюда). **Роль:** R6 Кодировщик. **Handoff:** WP context file = Human→Agent handoff; «Осталось» = Agent→Agent handoff.

**2d. Служебный семафор протокола не покрывает новую задачу (РП-561 Ф51, решение пилота 25.10; живой инцидент 24→25.10: закрытие дня открыло свой housekeeping-семафор и закрыло его, пилот продолжил новыми задачами без повторного preflight, обычная сессия не открывалась, `/session-close` позже отказал, самооткрытие задним числом запрещено).** Семафор `day-open`/`day-close`/`week-close`/`month-close` действует только пока идёт сам протокол. Как только он закрыт и пилот ставит НОВУЮ задачу, сначала повторный preflight (Kimi: `kimi-standalone-preflight.sh`; прочие агенты: проверка «есть ли открытая обычная сессия этого агента»), затем обычное открытие (`session-guard.sh open --wp N --agent <агент> --task "…"`, под заморозкой канона с `--isolate`; объявление намерения в п. 1а ниже, где оно есть, его не заменяет) ДО первого коммита и до любой записи в репо. Критерий «инцидент не воспроизводится»: сценарий «закрыли день → пришла новая задача → повторный preflight → обычное открытие → первый коммит» проходит без отказа `/session-close`. Опора: Ф50 (самый свежий семафор при нескольких циклах open/close в одной сессии) и Ф46 (хук `session-open-gate.sh` принимает только закрытый список housekeeping-причин). Кандидат на механизацию (не реализован, S-33): хук отказывает первому коммиту, если последний закрытый семафор агента housekeeping, а обычного открытого нет.

Отпечаток считать по серверу, не по рабочей копии: под заморозкой копия отстаёт, и запись, пришедшая на сервер после маркера, иначе не видна до 8 ч (найдено 03.11, Ф69): `GOV_REPO_ROOT="${IWE_WORKSPACE:-$HOME/IWE}/${IWE_GOVERNANCE_REPO:-DS-strategy}"; git -C "$GOV_REPO_ROOT" fetch -q origin && D=$(bash "${IWE_WORKSPACE:-$HOME/IWE}/scripts/wp-inbox.sh" digest --wp N --repo "$GOV_REPO_ROOT" --rev origin/main)`; пропуск, если `D` пусто ИЛИ `D` равно содержимому файла маркера. Фраза пилота «актуализируй РП-N» запускает шаг 3 вне зависимости от маркера.

   **Шаг 3a — Bundle.** Запустить детерминированный сборщик контекста, захватывая exit-код в ТОМ ЖЕ вызове Bash (не `2>&1` — bundle пишет `[WARN]` в stderr до первой строки stdout, слияние потоков ломает контракт «первая строка = машинный статус»):
   ```bash
   bash "${IWE_WORKSPACE:-$HOME/IWE}/.claude/scripts/wp-sync-bundle.sh" WP-N > /tmp/wp-sync-bundle-$$.md; BUNDLE_RC=$?; head -3 /tmp/wp-sync-bundle-$$.md; echo "bundle_rc=$BUNDLE_RC"
   ```
   Экономичный slug `$$` — только в пределах ОДНОГО вызова Bash-инструмента (переменная не переживает границу между вызовами) — работать с файлом и удалять его в этом же вызове или через путь, зафиксированный в этой же команде.

   | Exit | Значение | Действие |
   |------|----------|----------|
   | 0 | РП найден, `GIT_SYNC_STATUS: OK` или `NO_UPSTREAM` — третья строка `CARD_SOURCE: worktree` | читать вывод как обычно |
   | 0 | `GIT_SYNC_STATUS: STALE\|DIVERGED`, но третья строка `CARD_SOURCE: origin-pinned oid=<40hex> behind=N ahead=M` (WP-561 Ф24, 27.09) — карточки (целевая и связанные) прочитаны со снимка ЭТОЙ ревизии origin, рабочая копия не читалась | читать вывод как обычно — данные актуальнее рабочей копии; но ЛЮБАЯ запись — только в изолированной копии (`session-guard.sh open --isolate`); stderr bundle несёт предупреждение «ВСЕ файлы рабочей копии потенциально устарели» — процитировать пилоту одной строкой; маркер `wp-sync-<N>.done` НЕ ставить |
   | 1 | РП не найден | перейти к Ритуалу с пометкой «контекст не найден» |
   | 2 | ошибка парсинга frontmatter | перейти к Ритуалу, поднять stderr в «Требует внимания» |
   | 3 | `GIT_SYNC_STATUS: fetch_failed\|checker_unavailable`, ЛИБО `STALE\|DIVERGED` при отстающем remote-tracking ref (`refs/remotes/origin/<branch>` ≠ OID ls-remote — брокер Ф66 РП-530 ещё не подтянул) — свежесть данных не доказана, bundle читать нечего (WP-561 Ф20/Ф24) | см. ниже, НЕ переходить к 3b/3c молча |

   Exit 4 → не найдена библиотека wp-num.sh: ошибка установки, не «РП не найден»; сообщить пилоту и обновить шаблон.

   **`CARD_SOURCE` (третья машинная строка, WP-561 Ф24):** `worktree` — читалась рабочая копия (статус OK/NO_UPSTREAM); `origin-pinned oid=…` — читался снимок origin (рабочая копия STALE/DIVERGED, ref свежий); `worktree-forced` — `--force-sync`, читалась заведомо устаревшая копия. Sub-agent `wp-sync-actualizer` при `origin-pinned` работает как обычно (данные легитимны), diff применяется только в изолированной копии.

   **Exit 3 — рецепт по среде:** изолированная сессия (свой worktree, `session-guard.sh open --isolate`) → повторить Шаг 3a с `IWE_WORKSPACE` на этот worktree, он обычно свежий от `origin/main`. Канонический чекаут → не форсировать pull (AR.006, Pull-on-Touch); либо `session-guard.sh open --isolate` и повтор оттуда, либо, если пилот явно согласился работать по неполным данным, добавить `--force-sync` к вызову bundle и process дальше — статус `GIT_SYNC_STATUS`/`GIT_SYNC_OVERRIDE` из первых двух строк вывода обязательно процитировать пилоту одной строкой ДО решения, не молчать о нём.

   **Шаг 3b — Override (опционально).** `bash .claude/scripts/load-extensions.sh protocol-open sync` — exit 0 → `Read` файлы (alphabetic), они переопределяют дефолтное поведение шага 3c. Exit 1 → дефолт.

   **Шаг 3c — Дефолтное поведение по веткам (только при `BUNDLE_RC` = 0; при 3 — см. выше, не входить сюда без `--force-sync` или явного решения пилота):**
