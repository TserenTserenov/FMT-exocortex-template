## Git Staging — CRITICAL

**NEVER `git add -u`, `git add .`, `git add -A`** — these pick up changes from OTHER agents (Kimi/Hermes run in parallel) → incorrect attribution. Stage only specific files; before committing run `git diff --cached --name-only` and unstage anything unintended with `git restore --staged`. Examples → `memory/reference/agent-core.md`.

**After `git mv` in the same Work turn — verify content, not just the filename (issue #511).** The name list from `--name-only` may look correct while the diff is empty (rename without edits) or stale (edits made via Edit went to the wrong path). If a `git mv` of any file being committed occurred in this Work turn: run `git diff --cached <new_path>` before `git commit` and confirm the intended changes are present; commit only the new path after `git mv`, not the old one; separately verify the return code of `git add` before proceeding to `git commit`.

## Response Style — Pilot-Facing

Rules for clear responses to the pilot (full text — `memory/feedback_response_clarity_for_pilot.md`) — applies to chat, report synthesis, and post-action reports.

**Channel detector:** technical style — peer-Session transcripts, commit messages, PRs; plain language — chat with the pilot (unless the pilot themselves writes `grep`/`git`/paths/SHA) and §1–§4 of the report.md synthesis.

**Eleven rules (A1–A11), short:** A1 file path is not the subject (parenthetical only, after a plain-language verb); A2 English term only after its Russian description in parentheses; A3 first mention of a column/function — one-word explanation; A4 pre-flight: will the pilot be able to make a decision based on this sentence; A5 WHAT before HOW; A6 one consequence arrow per sentence; A7 "did → effect", `<details>` only when pilot-relevant details exist or are explicitly requested; A7.1 process log (SHA, commits, defects) — to the report file only, not to chat; A8 do not write a process log by default; A9 channel detector; A10 English status markers (exit/PASS/SHA) → plain-language words; A11 active voice on errors and findings.

## Code Style — Engineering (DP.SC.172)


**P-rules, short:** P0 before committing — run the repo's formatter and linter (tooling handles the mechanics); P1 a test without verifying an observable result is forbidden (`assert True` — code smell); P2 third repetition → extract a function, not `locals()[str]`; P3 dead branch/enum — delete it, do not keep "for compatibility"; P4 `except: pass` without logging is forbidden; P5 long function with mixed responsibilities / boolean mode flags — split it. Boundary: hard prohibitions (`git add -A`, secrets) belong in PACK-agent-rules (AR.*), not here. (Delivery/detectors per agent → `memory/reference/agent-core.md`.)

## Commit Attribution

Co-Authored-By is added only by an agent that actually participated in creating the commit (authorship, Review, substantive edit). Autonomous commits by other agents / Scripts — no trailer, if the agent did not participate.

If an agent only verified (checked) a commit — use `Verified-by: [Agent] <[email]>` or a "Verified by [role]" note in the commit body, not Co-Authored-By.

### For commits involving Kimi

**Method 1 (preferred — template):**
```bash
git commit -t ~/.git-commit-template-kimi -m "feat: description"
```

**Method 2 (manual — if template unavailable):**
```bash
git commit -m "feat: description" --trailer "Co-Authored-By: Kimi <noreply@moonshot.ai>"
```

**Never** commit without the trailer. If you forget — amend immediately:
```bash
git commit --amend --trailer "Co-Authored-By: Kimi <noreply@moonshot.ai>"
```

### For commits involving Codex (OpenAI)

```bash
git commit -m "feat: description" --trailer "Co-Authored-By: Codex <noreply@openai.com>"
```

Codex reads `AGENTS.md` natively; in peer sessions it acts as a critic (Review without file edits → `Analyzed-by: Codex <noreply@openai.com>`, following the same "editor vs. analyst" rule as Claude).

## Coordination Protocol (MCP Gateway)

> For agents with access to Local Gateway (Claude Code, Kimi). Hermes does NOT have MCP Gateway
> (`acquire_file_lock` / `release_file_lock`) — it uses `terminal` + `patch` directly,
> and reports to the pilot on push conflicts.

Before starting any edit task:

1. **Declare intention** (no lock needed):
   ```
   Tool: update_peer_status
   params: { "status": "working", "current_task": "<brief>", "files": ["relative/path/file.md"] }
   ```

2. **Acquire lock** before first Edit:
   ```
   Tool: acquire_file_lock
   param: canonical_file = relative path from IWE root
   ```

3. **Release lock** after commit:
   ```
   Tool: release_file_lock
   ```

4. On `lock_collision`: wait 30s and retry, or switch to another file.
