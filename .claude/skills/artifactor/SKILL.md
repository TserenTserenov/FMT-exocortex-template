# /artifactor — Артефактор-Постановщик

> **Роль:** DP.ROLE.058 Артефактор-Постановщик  
> **Триггер:** запрос без routing-tag (Маршрутизатор → Артефактор) или `/artifactor "текст"`  
> **Service Clause:** DP.SC.160

## When to use

Classifies raw pilot request → structured JSON {task_type, class, artifact, budget_estimate, confidence, routing_tag, resolution_path, schema_version, result_type, expected_result_kind, result_kind_resolution, hypothesis_relation}. Keyword-fast (<200ms) or Haiku fallback (<60s). Does NOT create WP or call executor.

## Обещание (контракт)

**Вход:** сырой текст запроса пилота (любой длины, без routing-tag)  
**Выход:** JSON, schema_version 4 (WP-575 Ф2 — поле `result_type`; Ф4 — поле `pair_link`) → stdout:

```json
{
  "task_type": "string",
  "class": "trivial | closed-loop | open-loop | problem-framing",
  "artifact": "string (одна строка на русском — существительное-результат)",
  "budget_estimate": "~Xh | ?",
  "confidence": "high | low",
  "routing_tag": "string",
  "resolution_path": "keyword | llm",
  "schema_version": 4,
  "result_type": "system | episteme | unresolved",
  "pair_link": {"status": "ok | mismatch | recurring_no_producer | needs_result | unresolved | agent_check_required", "producer": "session | имя системы | null", "output": "наблюдаемый результат срабатывания | null"},
  "expected_result_kind": "kind_id из PACK-digital-platform/pack/digital-platform/result-kinds-registry.yaml | null",
  "result_kind_resolution": "static | deferred-to-session | unresolved",
  "hypothesis_relation": "unclassified"
}
```

**Инвариант:**
- НЕ создаёт РП, НЕ вызывает исполнителя, НЕ задаёт уточняющих вопросов
- `confidence=high` только при keyword-пути; `confidence=low` при LLM-пути
- При запросе <5 слов: вернуть `{"error": "INSUFFICIENT_INPUT"}`, стоп
- `budget_estimate: "?"` только при `problem-framing` или полной неопределённости
- `result_type` (WP-575 Ф2, hard-distinctions.md №36) — Исполнитель (`system`: агент/скрипт/сервис — действующее) vs Информационный объект (`episteme`: документ/знание/правило — читаемое). Решается ДО имени и класса задачи, независимая ось от `expected_result_kind` — НЕ выводится из `kind_id` (кортеж `kind_id`/`task_type`/`class` присваивается одновременно, вывод из него нарушил бы «раньше имени и класса», и `kind_id` создавался для другого различения). `unresolved` — тип неочевиден → форсирует уточнение у пилота на WP Gate, классификатор НЕ гадает (тот же принцип, что `hypothesis_relation: "unclassified"` ниже).
- **Маршрутизация по `result_type`** (делает потребитель — `/wp-new`/WP Gate Ритуал, не сам Артефактор, тот же принцип, что и передача `hypothesis_relation` в WP Gate): `system` → обязательна проверка IntegrationGate (новизна инструмента/агента/скрипта/сервиса); `episteme` → Routing Gate (карта размещения документа/знания, `DP.KR.001 §5`); `unresolved` → уточнение у пилота до продолжения.
- `expected_result_kind` — дискриминатор ожидаемого kind-а результата (WP-481 Ф7, «не бывает общего результата»), НЕ показатель готовности проверки (`gate_ready` — забота `/verify`, не Артефактора)
- `result_kind_resolution: "unresolved"` — ни один kind реестра не подходит; классификатор НЕ подменяет ближайшим (анти-утечка в супертип)
- `result_kind_resolution: "deferred-to-session"` — мета-триггер (например `peer_session`), kind решается внутри самого процесса, не в момент классификации
- **stdout = CONFIG_ERROR** (exit 3) → реестр kind-ов не читается или устарел относительно `KEYWORD_MAP` (дрейф) — fail-closed, эскалировать пилоту, не игнорировать поле
- В handoff к WP Gate передать `hypothesis_relation: "unclassified"`. До выбора
  `tests | enables | responds | researches | operational` РП остаётся pending,
  а не запускается в работу.

## Стратегическое основание РП

Артефактор не вправе приписать РП гипотезу без решения пилота. Он обязан
передать в WP Gate вопрос о типе связи:

- `tests H-NNN` — РП проверяет одну ставку;
- `enables H-NNN` — делает её проверку измеримой или возможной;
- `responds H-NNN` — следует из вердикта;
- `researches` — ищет основание для новой гипотезы;
- `operational` — поддерживает норму, устраняет инцидент или исполняет обязанность.

Для первых трёх нужен один `H-NNN`. Для двух последних номер гипотезы не
подставляется. Связь `unclassified` видна в карточке РП и блокирует её запуск,
но не создание: это сохраняет обратимость и не ломает старые автоматизации.

## Algorithm

### Шаг 1. Keyword-lookup

Запустить скрипт (возвращает JSON или сигнал):

```bash
S="${IWE_SCRIPTS:-$HOME/IWE/scripts}"
PY3="$(bash "$S/lib/find-python3.sh")" && "$PY3" "$S/artifactor.py" "$ARGUMENTS"
```

Интерпретация результата:
- **stdout = JSON с `result_type: system|episteme`** (exit 0) → вернуть пилоту, стоп.
- **stdout = JSON с `result_type: unresolved`** (exit 0) → перейти к Шагу 2 и проверить смысл всего запроса, включая явное уточнение пилота. Keyword-ответ не учитывает уточнение после общего триггера («реализация плана»); повторять тот же keyword-ответ после уточнения нельзя. Если основной результат по-прежнему неизвестен, Шаг 2 сохраняет `unresolved` для вопроса потребителя.
- **stdout = INSUFFICIENT_INPUT** (exit 1) → вернуть `{"error": "INSUFFICIENT_INPUT"}`, стоп
- **stdout = NO_KEYWORD_MATCH** (exit 2) → перейти к Шагу 2
- **stderr содержит CONFIG_ERROR** (exit 3) → реестр kind-ов недоступен или устарел (дрейф) — эскалировать пилоту одной строкой, НЕ переходить к Шагу 2 (это не «нет keyword-совпадения», а поломка конфигурации)

### Шаг 2. LLM-классификация (при NO_KEYWORD_MATCH или unresolved)

Заполнить все поля, используя правила ниже. Вернуть JSON с `resolution_path: "llm"`, `confidence: "low"`, `schema_version: 4` и полем `pair_link` (Шаг 2.1). Для `expected_result_kind`/`result_kind_resolution` — та же логика, что у keyword-пути: подобрать `kind_id` из `PACK-digital-platform/pack/digital-platform/result-kinds-registry.yaml` по смыслу запроса; если ни один явно не подходит — `expected_result_kind: null`, `result_kind_resolution: "unresolved"` (не подменять ближайшим).

**Шаг 2.0 — тип результата (WP-575 Ф2, ПЕРВЫЙ вопрос, до имени и класса).** Прежде чем формулировать `artifact`/`class`, ответить: результат этой работы будет действующей системой (агент, скрипт, сервис, MCP-инструмент, бот, автоматизация — что-то, что будет ВЫПОЛНЯТЬСЯ) или информационным объектом (документ, знание, правило, отчёт, план — что-то, что будет ЧИТАТЬСЯ)?
- Если оба названы самостоятельными результатами без указания основного, или ни один не определён → `result_type: "unresolved"`, не гадать (та же дисциплина, что у `result_kind_resolution: "unresolved"`). Документ, который выдаёт создаваемый скрипт, — выход системы; документация к ней — сопроводительный результат. Это не делает тип неоднозначным, если основной результат явно указан. Описание сервиса без его реализации — `episteme`.
- Один признак явно доминирует → `result_type: "system"` или `"episteme"` соответственно.
- Пример: «создай нового бота для X» → `system`. «напиши руководство по Y» → `episteme`. «доделай хвосты РП-N» без указания что именно осталось → `unresolved` (может оказаться и кодом, и документом).

**Шаг 2.1 — связка «документ ↔ производитель» (WP-575 Ф4, пир-сессия 2026-10-27 с Kimi и Codex).** Система создаёт документ: кто формулирует документ, знает, что его производит; кто формулирует систему, знает, что она выдаёт. Пока `result_type` определён, задать встречный вопрос и заполнить `pair_link`. Проверка идёт по ЗАКАЗАННОМУ результату и по предмету приёмки («что пилот примет как готовое?»), а не по всем будущим экземплярам: многоразовый шаблон договора или один выпуск еженедельного отчёта сами по себе системы не требуют.
- `result_type: episteme`, вопрос «что производит этот документ?»:
  - разовая работа сессии пилота с агентом → `ok`, `producer: "session"`; существующая система → `ok`, `producer` = её имя;
  - приёмка — не файл, а процесс, который создаёт новые документы сам («автоматизируй подготовку отчёта», «чтобы каждый месяц собирался») → `mismatch`, подсказка: `result_type: system`;
  - заказан один документ (приёмка — файл), но пилот сам говорит, что такие документы понадобятся снова, и способ подготовки не назван → `recurring_no_producer`;
  - неизвестно → `unresolved`.
- `result_type: system`, вопрос «какой наблюдаемый результат возникает при срабатывании?» (документ, событие, действие или изменение состояния — не только документ):
  - назван повторяемый наблюдаемый результат → `ok`, `output` = он;
  - результат не назван → `needs_result`;
  - результат разовый, по сути документ или разовая работа → `mismatch`, подсказка: `result_type: episteme`;
  - неизвестно → `unresolved`.
- `result_type: unresolved` → `pair_link.status: "unresolved"`, `producer`/`output` — `null`.
- Блокирующие статусы — `mismatch`, `needs_result`, `unresolved`: Артефактор сам вопросов пилоту не задаёт (инвариант ниже), а возвращает статус, и потребитель (`/wp-new`) останавливает регистрацию РП до ответа пилота. `recurring_no_producer` не блокирует: потребитель записывает сигнал и задаёт один вопрос «завести систему отдельным РП?».
- Keyword-путь (Шаг 1) связку не проверяет и всегда возвращает `agent_check_required`: потребитель проверяет её сам по тексту запроса и спрашивает пилота только при нехватке сведений. Слова «каждый раз», «по событию», «автоматически» — подсказка для вопроса, не детектор: наличие слова границу не определяет.

**Шаг 2.2 — сверка названия с Реестром понятий и родов (WP-575 Ф5, решение пилота 27.10).** Реестр понятий и родов живёт в паке `PACK-digital-platform`. Если пак не установлен (обычная установка шаблона) — шаг пропусти: `scripts/artifactor.py --check-registry` в этом случае сам возвращает код 0 со словом `no-pack`, и РП создаётся без сверки названия. Если пак установлен — шаг обязателен целиком, а нечитаемый реестр или `scripts/concept-kind.py` — отказ, его эскалируй пилоту. Слово-голова названия — первое слово `artifact`, и лучше, чтобы это было существительное — предмет результата: не «Системный журнал», «Нового реестр», «Два реестра», «Для реестра», «Мини реестр», а «Журнал системы», «Реестр нового формата», «Реестр из двух частей». Если название всё же начинается с прилагательного, местоимения, числа, предлога, союза или приставки, жёсткого отказа нет (списки окончаний неполны и ошибаются на существительных вроде «Описание», «Решение», «Слой»): скрипт требует ответа ИИ о предмете результата и выдаёт предупреждение пилоту. Дальше три исхода:
1. **Реестр знает слово, род противоречит `result_type`** → жёсткий отказ. Для `system` допустим только род «система»; для `episteme` — «описание», «документ», «план работ», «набор». Остальные роды (метод, работа, деятельность, состояние, характеристика, роль, способность) именем результата РП не бывают.
2. **Слова нет в реестре, оно неоднозначно или голова составная** («Характеристики и состояния …») → решаешь ты, ИИ. Возьми проверочный вопрос рода из реестра (`"$PY3" "$S/concept-kind.py" --agent claude lookup <слово> --claim <род>`, где `S` и `PY3` — как в Шаге 1), ответь на него и запиши род и ответ. Не рассуждай по аналогии со словами: слово — подсказка, решает вопрос.
3. **Неуверенность → пилоту.** Если у слова два правдоподобных рода (например, «Библиотека»: набор документов или здание-хранилище; «Хранилище»; «Контур» — расплывчатое слово, лучше предложить конкретное), не угадывай: отметь неуверенность и спроси пилота. Если реестр сам называет слово неоднозначным, вопрос пилоту обязателен всегда.
- Настоящий замок — `scripts/create-wp.sh`, он вызывает `scripts/artifactor.py --check-registry`. Твой ответ передаётся флагами `--name-kind <род>` и `--name-kind-answer "<ответ на проверочный вопрос>"`; при сомнении добавь `--name-kind-unsure`, а решение пилота передай дословно в `--name-kind-pilot`. Без ответа на вопрос РП не создаётся.
- Обход всего замка — `--registry-waiver "причина"`, только по слову пилота; причина пишется в карточку. Источник проверки в карточке: `registry_check` = `registry` (слово в реестре), `ai` (решил ИИ), `pilot` (решил пилот), `waived` (обход), `no-pack` (пак `PACK-digital-platform` не установлен, сверки не было), `skipped` (аварийный обход Артефактора).
- Каждая сверка названия, дошедшая до реестра, пишется в журнал утилиты поиска рода (отказы до чтения реестра — нет: тип результата не определён, реестр не читается). Слова, решённые ИИ или пилотом, — кандидаты в реестр, их раз в неделю утверждает пилот.
- Быстрый путь по ключевым словам эту сверку не проводит: её всё равно проведёт замок при создании РП.

**Правила `class`:**

| Класс | Критерий |
|-------|---------|
| `trivial` | Протокол без неопределённости (day-open, week-close, peer-сессия) |
| `closed-loop` | Чёткая спецификация + известный метод (баг-фикс, миграция, ревью, триаж) |
| `open-loop` | Нет спецификации, нужно генерировать (контент-план, диагностика, сценарии) |
| `problem-framing` | Расплывчато, метод неизвестен (идеи, концепции, «что-то придумать с X») |

При сомнении — выбирать более широкий класс (open-loop, не closed-loop).

**Правила `artifact`:** одна строка на русском, первое слово — существительное, обозначающее документ, систему или состояние системы (не процесс/действие над ним — «Разбор X», «Анализ X», «Проверка X» не годятся, даже когда сами по себе грамматически существительные).  
Примеры: «Список тем для трёх постов», «Отчёт диагностики латентности», «Задание на сценарии».
Не так: «Разбор 88 неразобранных коммитов» (описывает действие) → так: «Реестр неразобранных коммитов ветки X» (описывает артефакт-результат).

**Общий тест «процесс → результат» (WP-7 Ф140, peer-session 2026-09-11 с Kimi+Codex).** Частные примеры выше не ловят отглагольные существительные без объекта X («Оплата», «Миграция», «Интеграция», «Синхронизация») — формально существительные, но по смыслу называют само действие. Перед тем как принять `artifact`:
1. Подставь кандидат обратно в глагол: «Оплата»→«оплатить», «Интеграция»→«интегрировать», «Синхронизация»→«синхронизировать», «Миграция»→«мигрировать». Подстановка получилась естественной → кандидат называет процесс, не результат — отклонить.
2. Спроси: «что конкретно будет существовать или в каком проверяемом состоянии окажется система после этой работы?» — назови этот объект/документ/состояние, не саму работу.
3. Назови предмет, который после работы можно открыть и сверить: файл, папку, сервис или проверяемое состояние. Первое слово — имя этого предмета («Реестр», «Регламент», «Канал», «Отчёт», «Рабочие пакеты»).

Причастие на старом существительном оставляет прежний объект и клеит к нему статус. Так не называть.
- Не «Реализованный план». План уже был. Появляются рабочие пакеты из этого плана, их карточки и файлы. Имя: «Рабочие пакеты из плана».
- Не «Настроенный канал оплаты». Предмет — сам канал. Имя: «Канал оплаты Мастерской IWE через Aisystant и Telegram».
- Не «Актуализированная стратегия». Предмет — документ стратегии. Имя: «Документ стратегии».
- Не «Ротированные секреты». Предмет — записи секретов в хранилище. Имя: «Секреты в хранилище».

Пример: не «Оплата Мастерской IWE через Aisystant и Telegram-канал» (оплата→оплатить — сама работа), а «Канал оплаты Мастерской IWE через Aisystant и Telegram».

Тест применяется и к keyword-пути (Шаг 1) — но там НЕ рантайм-проверкой (это нарушило бы контракт «<200ms, без LLM»), а разовым аудитом `KEYWORD_MAP` в `artifactor.py`: значение `artifact` каждой записи обязано проходить тот же тест на момент добавления/правки записи.

**Имя системы (`result_type: system`): спор между кандидатами (WP-575 Ф3, peer-session 2026-10-27, Claude+Kimi+Codex).** Тест «процесс → результат» отсеивает названия процесса, когда заказанный результат — система, но не выбирает между двумя допустимыми существительными для одной системы. Для системы предмет, который можно «открыть и сверить», — работающий сервис, поэтому система-исполнитель вправе носить имя по роли («Аналитик чата»). Когда кандидатов несколько:
1. Определить границу заказанного результата: какую систему просит пилот, а не весь продукт вокруг неё.
2. Выписать сценарии использования этой системы: кто и зачем её запускает или читает её результат.
3. Назвать главную функцию — одно действие системы, создающее ценность в этих сценариях. Источник — факт из запроса или сценария, а не вкус автора.
4. Сравнить кандидатов: имя по главной функции или роли («Аналитик чата») предпочтительнее имени по пассивному свойству или внутренней детали («Память чата»), если заказанный результат — сервис, выполняющий эту функцию. Если заказан именно сервис по этому свойству (сохранение и выдача контекста, поиск по каталогу), имя по свойству верно: «Хранилище», «Каталог», «Индекс» — допустимые имена систем, когда пилот просит такой сервис.

Это эвристика LLM-шага, не проверка по слову: слова «хранит», «память», «каталог» не запрещены. Спорный выбор между кандидатами при равных доводах — вопрос пилоту, а не решение автора.

Пример (РП-612): заказана система, которая разбирает сообщения чата и выдаёт выводы; главная функция — анализ. «Аналитик чата» называет эту функцию — принято пилотом. «Память чата» подошла бы только к заказанному сервису сохранения и выдачи контекста.

**Правила `budget_estimate`:**
- `trivial` → `~0.5h`
- `closed-loop` → `~2h` (если нет конкретного числа в запросе)
- `open-loop` → `~3h`
- `problem-framing` → `?`

**Поле `routing_tag`** = значение `task_type` (snake_case).

### Шаг 3. Вернуть результат

Вывести JSON в stdout. Без дополнительных пояснений.
