# Диспетчер: Сессия стратегирования (monthly)

> **Роли:** Стратег ведёт стратегическую сверку, Плановик собирает неделю, человек утверждает решения · **Частота:** 1 раз в месяц (первая неделя) · **Длительность:** ~45–60 мин
>
> Это **полный вариант** с каскадом ВДВ. Еженедельный короткий вариант — `strategy-session-weekly.md`.

Сессию проводит личный Штаб стратегирования. Стратег и Плановик обозначают назначения внутри Штаба; этапы 0–8 ниже не являются отдельными системами. Состоявшаяся сессия — эпизод работы, а ожидаемые входы и выходы этапов описаны в `.claude/skills/strategy-session/SKILL.md`.

## Стиль общения с пилотом

Все ответы в сессии — **режим «на пальцах»** (S-37, A1-A11):
- Только русский язык. Английский термин — только в скобках после русского описания.
- Технические метки типа «gate: skip», «exit 0», имена файлов — **не писать в чат**. При пропуске шага (gate: skip-if-empty) — сообщи пилоту коротко («Нерегулярных блоков нет»), затем **СТОП — жди ответа, не переходить молча**.
- Пути к файлам — только в скобках после русского глагола, никогда подлежащим.
- Объяснять через «что это значит для плана», не через «что сделал Клод».

## Предусловие

Черновик WeekPlan (`status: draft`) уже создан сценарием `session-prep` (Пн 04:00). Если черновика нет — сообщи пользователю и предложи запустить `session-prep`.

## Resume — обнаружение незавершённой сессии

**До чтения шага 00** — проверить `current/WeekPlan W*.md` на наличие раздела `## Итоги Strategy Session` с незакрытыми пунктами (⏳):

```
grep -l "⏳" current/WeekPlan\ W*.md
```

Если найден WeekPlan с ⏳ в разделе сессии:
- Сообщи пилоту: «Найдена незавершённая сессия W{N}. Последний выполненный шаг: [найди последний ✅]. Возобновить с шага [N+1] или начать заново?»
- **СТОП — жди ответа пилота.**
- Возобновить → читать файл шага N+1. Начать заново → шаг 00.

Если незавершённой нет → сразу шаг 0.0.

## Шаг 0.0 — Обзор сессии (обязательно, один раз, до чтения шага 0)

Если сессия не возобновляется (раздел Resume выше не сработал) — прежде чем читать файл шага 0, вывести пилоту одним сообщением, человеческим языком (без путей, без технических меток шлюза), список этапов именно этого варианта сессии из таблицы «Последовательность шагов» ниже — название каждого этапа одной строкой. Затем **СТОП — жди ответа пилота**, и только после него переходить к шагу 0.

## Инструкция для Claude (execution semantics)

> **БЛОКИРУЮЩЕЕ — шаг за шагом.** Нарушение = потеря смысла сессии: пилот не внёс свои данные, решения приняты без него.

**Правило одного шага:**
1. Прочитать файл ТЕКУЩЕГО шага.
2. Объявить пилоту одной строкой: название шага + какие данные будут использованы (поле «Вход» из таблицы ВДВ этого шага, человеческим языком).
3. Выполнить шаг, вывести результат пилоту.
4. **СТОП. Ждать следующего сообщения пилота.**
5. Только после ответа пилота — читать файл СЛЕДУЮЩЕГО шага.

**ЗАПРЕЩЕНО:**
- Читать `strategy-session-weekly/steps/*` через glob или несколько файлов за один ход.
- Переходить к следующему шагу без ответа пилота (даже если gate = `auto`).
- Объединять несколько шагов в один ответ.

**РАЗРЕШЕНО:** Read только файл шага, явно указанного на текущей позиции последовательности.

**После compaction / восстановления контекста:** правило действует без исключений. История того, что было сделано до compaction, не отменяет требование ждать пилота на каждом шаге.

## Jump-обработка

Если пилот во время сессии решает вернуться к шагу 03:
1. Прочитай `jump-handler.md`
2. Следуй алгоритму jump-handler
3. После обработки jump — вернись к шагу 04

## Софт-гейт при ad-hoc jump

Если пилот пишет «назад к шагу 3» без явного сигнала critical — предупреди:
> «Возврат к НЭП сбросит шаги 4 (стратегическая сверка) и 5a/5b/5c (калибр). Продолжить?»

## Проверка результата перед сессией (РП518 Ф17, решение пилота 19.10.2026)

Если перед сессией стратегирования нужна независимая проверка материала (например, кандидатов для шага плана или анализа ограничения месяца) — эта проверка **не ведётся как часть этого пошагового ритуала** и не подменяет правило «один шаг, стоп, жди пилота» выше. Она идёт отдельно, до начала этой процедуры: либо диалогом с другим агентом (пир-сессия, Codex/Kimi), либо разбором силами одного агента (например, холодное ревью субагентом) — в обоих случаях задача проверяющего — посмотреть, что сделал первый, не согласиться с ним автоматически. Результат (отчёт или вывод проверки) становится одним из источников входных данных конкретного шага. При объявлении шага (см. «Правило одного шага», п.2) — если для этого шага есть релевантный результат такой проверки, назвать его явно как часть «Вход».
