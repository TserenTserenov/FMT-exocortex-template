# Диспетчер: Сессия стратегирования (monthly)

> **Роли:** Стратег ведёт стратегическую сверку, Плановик собирает неделю, человек утверждает решения · **Частота:** 1 раз в месяц (первая неделя) или по прямой просьбе пилота провести полную сессию · **Длительность:** ~45–60 мин
>
> Это **полный вариант** с каскадом ВДВ. Еженедельный короткий вариант — `strategy-session-weekly.md`.

Сессию проводит личный Штаб стратегирования. Стратег и Плановик обозначают назначения внутри Штаба; этапы 1–10 из таблицы «Этапы сессии» ниже не являются отдельными системами. Состоявшаяся сессия — эпизод работы; вход и выход каждого этапа заданы таблицами ВДВ его файлов шагов.

## Стиль общения с пилотом

Все ответы в сессии — **режим «на пальцах»** (S-37, A1-A11):
- Только русский язык. Английский термин — только в скобках после русского описания.
- Технические метки типа «gate: skip», «exit 0», имена файлов — **не писать в чат**. При пустом этапе (gate шага: skip-if-empty) — сообщи пилоту коротко («Нерегулярных блоков нет»), затем **СТОП — жди ответа, не переходить молча**.
- Пути к файлам — только в скобках после русского глагола, никогда подлежащим.
- Объяснять через «что это значит для плана», не через «что сделал Клод».

## Предусловие

Черновик WeekPlan (`status: draft`) уже создан сценарием `session-prep` (Пн 04:00). Если черновика нет — сообщи пользователю и предложи запустить `session-prep`.

## Resume — обнаружение незавершённой сессии

**До чтения файлов этапа 1** — проверить `current/WeekPlan W*.md` на наличие раздела `## Итоги Strategy Session` с незакрытыми пунктами (⏳):

```
grep -l "⏳" current/WeekPlan\ W*.md
```

Если найден WeekPlan с ⏳ в разделе сессии:
- Сообщи пилоту: «Найдена незавершённая сессия W{N}. Последний пройденный этап: [номер и название по последнему ✅]. Возобновить со следующего этапа или начать заново?»
- **СТОП — жди ответа пилота.**
- Возобновить → читать файлы следующего этапа по таблице «Этапы сессии». Начать заново → к обзору сессии ниже.

Если незавершённой нет → сразу к обзору сессии ниже.

## Обзор сессии (обязательный гейт, один раз, перед этапом 1)

Выполняется в обоих случаях свежего старта — Resume не нашёл незавершённую сессию, или пилот выбрал «начать заново». Прежде чем читать файлы этапа 1, вывести пилоту одним сообщением список этапов этого варианта из таблицы «Этапы сессии» ниже: номер и название каждого этапа ровно как в колонках «№» и «Этап», одной строкой на этап, без пересказа своими словами, без кодов файлов и технических меток. Затем **СТОП — жди ответа пилота**, и только после него переходить к этапу 1.

## Инструкция для Claude (execution semantics)

> **БЛОКИРУЮЩЕЕ — этап за этапом.** Нарушение = потеря смысла сессии: пилот не внёс свои данные, решения приняты без него.

**Этап ≠ файл шага.** Пилот видит этапы (колонка «№», 1…10). Поле `gate` в файле шага говорит, нужен ли этому шагу вход пилота (`user`), не нужен (`auto`) или шаг может оказаться пустым (`skip-if-empty`); где остановка — решает этап, не `gate` шага. За этапом стоит один или несколько файлов шагов (колонка «Файлы шагов»); их коды (`05a`, `06b` и т. п.) — внутренние, на них завязаны отметки `gate_reviews` плана недели, пилоту их не называть. Остановка — одна на этап.

**Правило одного этапа:**
1. Прочитать файлы шагов ТЕКУЩЕГО этапа, по порядку из колонки «Файлы шагов». Файл, помеченный «запись», в этом ходе не читать (см. п. 6).
2. Объявить пилоту одной строкой: номер и название этапа + какие данные будут использованы (поле «Вход» из таблицы ВДВ шагов этапа, человеческим языком).
3. Выполнить шаги этапа и вывести пилоту один общий результат. Остановки и вопросы «продолжить к …?» внутри файлов шагов этого этапа, кроме последнего, пропустить: этап кончается один раз.
4. **СТОП. Ждать следующего сообщения пилота.**
5. Только после ответа пилота — читать файлы СЛЕДУЮЩЕГО этапа.
6. Шаг «запись» (фиксирует уже принятое решение пилота, своего решения не требует) выполняется в начале следующего хода, сразу после ответа пилота и до файлов следующего этапа; пилоту — одна строка о том, что записано. Если ответ пилота — не решение (вопрос, уточнение, «скорректируй»), этап не закончен: ничего не записывай, доработай результат этапа и снова остановись.

**Отметки шагов в плане недели.** Если во frontmatter черновика плана недели есть поле `gate_reviews`: на этапе 1 запиши рядом `session_variant: monthly` или `session_variant: weekly` (вариант, который выбрал диспетчер), а шагам вне выбранного варианта поставь `status: not_applicable`. Проверка подтверждения плана ждёт отметки только шагов этого варианта. Когда пилот ответил решением по этапу (в начале следующего хода, вместе с шагом «запись»), поставь каждому шагу этого этапа, у которого есть ключ в `gate_reviews`, `status: reviewed`, `reviewed_at: <дата и время>` и `pilot_quote: <короткая дословная цитата ответа>`; для `06a` — ещё `pilot_decision` по правилам его файла. Пустой этап (нечего разбирать) — `status: not_applicable`. Ответ пилота — не решение → отметку не ставь. Шаги без ключа в `gate_reviews` (00, 05a, 07) не отмечаются. Поля `gate_reviews` нет — весь этот абзац пропусти.

**ЗАПРЕЩЕНО:**
- Читать `strategy-session-weekly/steps/*` через glob или файлы другого этапа.
- Переходить к следующему этапу без ответа пилота (даже если gate шага = `auto`).
- Объединять несколько этапов в один ответ.
- Показывать пилоту номера или названия этапов не из таблицы ниже.

**РАЗРЕШЕНО:** Read только файлов шагов этапа на текущей позиции последовательности.

**После compaction / восстановления контекста:** правило действует без исключений. История того, что было сделано до compaction, не отменяет требование ждать пилота на каждом этапе.

## Этапы сессии

> **Единственный источник состава и порядка этапов** для полной и короткой сессии. Короткая сессия (`strategy-session-weekly.md`) берёт строки с «да» в колонке «Короткая», с теми же номерами и названиями; диспетчер скилла `strategy-session` своей таблицы этапов не держит. Новый этап, переименование или перестановка — только здесь.

| № | Этап | Ведёт / решает | Файлы шагов (`strategy-session-weekly/steps/`) | Короткая |
|---|------|----------------|-----------------------------------------------|----------|
| 1 | Открытие | Исполнитель / человек | `00-open.md` | да |
| 2 | Ревью недели и стоп-лист | Плановик / человек | `01-review.md` | да |
| 3 | Нерегулярные вопросы | По вопросу / человек | `07-irregular.md` | да |
| 4 | Разбор входящих | Стратег / человек | `02-inbox.md` | да |
| 5 | Неудовлетворённости | Стратег / человек | `03-dissatisfactions.md` | нет |
| 6 | Стратегическая сверка | Стратег / человек | `04-strategy-sync.md` | да |
| 7 | Калибр | Исполнитель / человек | `05a-measurement.md`, `05b-recommendation.md`, `05c-tracking.md` (запись) | нет |
| 8 | План недели: кандидаты | Плановик / человек | `06a-pool.md` | да |
| 9 | План недели: бюджет и доводка | Плановик / человек | `06b-budget.md`, `06c-finalize.md` | да |
| 10 | Утверждение | Человек / исполнитель сохраняет | `08-confirm.md` | да |

Нерегулярные вопросы стоят третьими, а не в конце: срочные темы из открытия и сработавшие триггеры обхода Backlog — вход для неудовлетворённостей, стратегической сверки и проверки состава недели короткой сессии. Этап с пустым содержимым (открытие без повестки, нерегулярных вопросов нет) не выбрасывается молча: одна строка пилоту и остановка, как в его файле шага.

## Завершение monthly-сессии

Только после успешного шага 8 (`08-confirm.md`, этап 10 «Утверждение»: человек утвердил решения, результаты синхронизированы) выполнить расширения `strategy-session after` **один раз за завершённую сессию**, в том числе при переходе из weekly. До завершения шага 8, при прерывании или ожидании ответа пилота after не запускать. При возобновлении незавершённой сессии выполнить after после её успешного завершения. «Один раз» — правило для агента, а не механическая гарантия: после аварийного обрыва шага 8 сначала проверь по записи сессии и результатам расширений, не выполнялись ли они уже, и не дублируй выполненное.

```bash
GOV_WT="<записанный путь>" bash "{{WORKSPACE_DIR}}/.claude/scripts/load-extensions.sh" strategy-session after
```

Код 0 — прочитать и выполнить каждый возвращённый файл (включая `strategy-session.after.*.md`); код 1 — расширений нет, пропустить. Другой код — сообщить ошибку загрузки, не считать расширения выполненными. `GOV_WT` — та же активная рабочая копия, которую выбрал диспетчер скилла `strategy-session` (его раздел «Рабочая копия governance-репозитория»); повторно её не создавать. Вызов здесь заменяет weekly-after при переходе из weekly, не дополняет его вторым вызовом.

## Jump-обработка

Если пилот во время сессии решает вернуться к этапу 5 «Неудовлетворённости» (шаг `03`):
1. Прочитай `jump-handler.md`
2. Следуй алгоритму jump-handler
3. После обработки jump — вернись к этапу 6 «Стратегическая сверка»

## Софт-гейт при ad-hoc jump

Если пилот пишет «назад к неудовлетворённостям» без явного сигнала critical — предупреди:
> «Возврат к неудовлетворённостям (этап 5) сбросит этапы 6 «Стратегическая сверка» и 7 «Калибр». Продолжить?»

## Проверка результата перед сессией (РП518 Ф17, решение пилота 19.10.2026)

Если перед сессией стратегирования нужна независимая проверка материала (например, кандидатов для этапа плана или анализа ограничения месяца) — эта проверка **не ведётся как часть этого пошагового ритуала** и не подменяет правило «один этап, стоп, жди пилота» выше. Она идёт отдельно, до начала этой процедуры: либо диалогом с другим агентом (пир-сессия, Codex/Kimi), либо разбором силами одного агента (например, холодное ревью субагентом) — в обоих случаях задача проверяющего — посмотреть, что сделал первый агент, не согласиться с ним автоматически. Результат (отчёт или вывод проверки) становится одним из источников входных данных конкретного этапа. При объявлении этапа (см. «Правило одного этапа», п.2) — если для него есть релевантный результат такой проверки, назвать его явно как часть «Вход».
