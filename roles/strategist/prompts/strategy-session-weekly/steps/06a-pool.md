1. **Candidate pool** — пройди предложенные РП из черновика session-prep:
   - (a) активные R{N} месяца
   - (b) carry-over с приоритизацией
   - (c) предложения из inbox triage (шаг 02)
   - (d) новые РП из калибра (шаг 05b, если созданы)

   **Ставка (если в инсталляции подключён журнал гипотез, `current/hypotheses-log.md`):** у каждого РП пула отметь, на какую гипотезу он делает ставку (номер записи или «нет ставки»). РП без ставки и без прямой привязки к активному R{N} месяца — кандидат на «не берём» в 06b, не берётся по умолчанию тихо. Журнала нет в инсталляции → пропусти этот пункт, не блокирует пул.

2. **Режим работы (триада) — две независимые оси, не путать.**

   **Ось 1 — режим ТВС (текущее / важное / срочное):** для каждого РП определи режим по конвейерной модели (см. различение [[Текущее ≠ Важное ≠ Срочное (ТВС)]]):
   - 🔥 **Срочное** — угроза остановки конвейера (прод упал, биллинг сломан, блокирует других агентов/пользователей, потеря данных, security-critical). **Только это.** Срочное в норме НЕ планируется в неделю — оно прерывает и чинится немедленно; если попало в пул, значит конвейер уже стоит.
   - 🟡 **Важное (развитие)** — поднимает норму выше прежней (новая способность, модернизация, стратегический R{N}). Это сердцевина стратегической недели: важное системно вытесняется текучкой и ложно-срочным, поэтому защищается осознанно.
   - 🟢 **Текущее (текучка)** — штатная операционная работа, держит конвейер в плановой норме (поддержка, рутина, операционные НЭП).

   **Ось 2 — дедлайн (ортогонально режиму):** есть ли согласованный момент передачи дальше? Дедлайн может стоять на ЛЮБОМ из трёх режимов и сам по себе НЕ делает РП срочным (см. [[Дедлайн ≠ Срочность]]). Помечай дедлайн отдельной меткой `⏰ до DD.MM`, не повышай им режим.

   **Критическая проверка (частая ошибка):** «приближается дедлайн» ≠ «срочное». Сильная неудовлетворённость / высокая мотивация ≠ «срочное» — это важное. Срочное = только физическая угроза остановки конвейера.

3. **Приоритет = функция режима + дедлайн + ТОС.** Порядок взятия в неделю: реальное 🔥срочное (если ещё не закрыто) → 🟡важное под ТОС недели и активные R{N} → 🟡важное с близким ⏰дедлайном → 🟢текучка (минимально необходимая для удержания нормы). Цель недели — защитить квоту 🟡важного, а не дать текучке и ⏰дедлайнам вытеснить развитие.

4. **Свежесть данных и машинное подтверждение (WP-518, 08.09.2026).** Если
   черновик пришёл от `week-open-scaffold.sh`, состав таблицы уже решён
   детерминированно кодом (`week_pool_manifest.py`), не твоим суждением —
   найдено 07.09: свободное суждение LLM внутри промпта расходилось с
   заявленным правилом отбора (6 исключённых РП сами были P1).

   - Если в шапке секции «План на неделю» есть строка, начинающаяся с
     `⚠️ рабочее дерево` (все 4 варианта баннера — отстаёт / разошлось /
     `git fetch` не удался / нет upstream-ветки — начинаются одинаково,
     проверяй по префиксу, не по конкретной формулировке) — **СТОП**: скажи
     пилоту, что состав пула может быть неактуален, предложи синхронизировать
     чекаут и пересобрать черновик заново. Не продолжай подтверждение на этом
     баннере.
   - Покажи пилоту таблицу пула как есть. Если пилот спрашивает, почему
     конкретный РП не попал в пул — не сочиняй причину: у отбора уже есть
     `reason_code` на каждой записи (создаётся кодом, не тобой); объясни
     значение `cap_exceeded_rank_N_of_M` (не хватило места в shortlist по
     приоритету) как есть, включая честную оговорку — соответствие
     месячному фокусу сегодня НЕ входит в ранжирование (открытый пункт
     РП-518), только приоритет + номер РП.
   - **Подтверждение пилота — записываемый факт, не формальность.** После
     обсуждения дождись ЛИТЕРАЛЬНОГО ответа пилота на предъявленный пул
     (не молчаливого перехода к следующему шагу) и запиши в WeekPlan
     frontmatter `gate_reviews.06a`:
     - `pilot_decision: approved | changes_requested | rejected`
     - `pilot_quote`: короткая дословная цитата ответа пилота
     - `status`: `reviewed` (не `confirmed` — это поле файла целиком, шаг 08)
     `content_hash` уже записан автоматически (`week-open-llm-fill.py`) —
     не переписывай его вручную. Если состав пула изменился в разговоре
     (пилот попросил добавить/убрать РП вручную) — пул нужно пересобрать
     заново скриптом, не редактировать таблицу от руки: иначе
     `content_hash` перестанет соответствовать реально показанному составу,
     и шаг 08 упадёт на сверке (`strategy-session-checks-runner.sh`).
