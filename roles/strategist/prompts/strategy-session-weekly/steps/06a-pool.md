# Step 06a: План недели — кандидаты

## ВДВ

| | |
|---|---|
| **Вход** | Черновик WeekPlan, активные R{N} месяца, carry-over, предложения из inbox, новые РП из калибра (05b), рамка месяца недели (`current/monthly-priorities.md` своего месяца, иначе «Фокус» этого месяца в `docs/Strategy.md`; WP-518, 08.09.2026 — раньше молчаливо предполагалось, что шаг 04 уже прочитал её ранее в этой же сессии; найдено 07.09, что это не всегда так) |
| **Действие** | Сформировать пул кандидатов, проставить приоритеты |
| **Выход** | Candidate pool с приоритетами (🔴/🟡/🟢/⚪) |

## Инструкция для Claude

> Метод: `PD.METHOD.017` Work Product Selection.

**Новый кандидат ещё не зарегистрированный РП.** У существующих РП сохраняй номера; новым не назначай окончательные номера и не создавай карточки на этом шаге. После утверждения конкретного списка в шаге 08 зарегистрируй выбранные новые РП через `/wp-new` по разделу «Регистрация РП перед утверждением» скилла `strategy-session`.

0. **Обязательная сверка с месячной рамкой (WP-518, 08.09.2026) — по аналогии с
   уже обязательным обходом `Backlog.md` в шаге 07.** Найдено живьём 07.09:
   целая сессия пересборки недели ни разу не сверилась с уже принятым планом
   сентября (`docs/Strategy.md` секция «Фокус: {месяц}»), хотя шаг 04
   формально существует именно для этого — сессия просто не прошла по шагам
   00→08 целиком.

   - Прочитай рамку месяца — `current/monthly-priorities.md`, если в его frontmatter `period` совпадает с месяцем недели; иначе раздел «Фокус: <месяц> <год>» этого месяца в `docs/Strategy.md`; раздел другого месяца рамкой не считается.
   - Опциональный ускоритель (в поставку шаблона не входит, issue #1100):
     если в инсталляции есть `strategy-focus-hash.sh` — сначала в
     `$GOV_WT/scripts/` (автоматизация самого репозитория стратегии), затем
     в `$IWE_SCRIPTS/` — вызови `bash "<найденный путь>" "$GOV_WT" "<YYYY-MM месяца недели>"` и
     запиши результат как `gate_reviews.06a.monthly_context_hash` в WeekPlan.
     Это не доказывает, что ты осмыслил текст — только то, что предъявление
     пула привязано к конкретной, зафиксированной по хешу версии рамки
     месяца на момент предъявления (не путать с когнитивной гарантией).
   - Скрипта нет на этой установке (штатно для чистой установки) — не
     блокировать: сообщи пилоту «сверка с месячной рамкой без машинной
     привязки версии», продолжай без хеша.

1. **Candidate pool** — пройди предложенные РП из черновика session-prep:
   - (a) активные R{N} месяца
   - (b) carry-over с приоритизацией
   - (c) предложения из inbox triage (шаг 02)
   - (d) новые РП из калибра (шаг 05b, если созданы)

   **Ставка (если в инсталляции подключён журнал гипотез, `current/hypotheses-log.md`):** у каждого РП пула отметь, на какую гипотезу он делает ставку (номер записи или «нет ставки»). РП без ставки и без прямой привязки к активному R{N} месяца — кандидат на «не берём» в 06b, не берётся по умолчанию тихо. Журнала нет в инсталляции → пропусти этот пункт, не блокирует пул.

2. **Режим работы (триада) — две независимые оси, не путать.**

   **Ось 1 — режим ТВС (текущее / важное / срочное):** для каждого РП определи режим по конвейерной модели (см. различение [[Текущее ≠ Важное ≠ Срочное (ТВС)]]):
   - 🔥 **Срочное** — угроза остановки конвейера (прод упал, биллинг сломан, блокирует других агентов/пользователей, потеря данных, security-critical). **Только это.** Срочное в норме НЕ планируется в неделю — оно прерывает и чинится немедленно; если попало в пул, значит конвейер уже стоит.
   - 🟡 **Важное (развитие)** — поднимает норму выше прежней (новая способность, модернизация, стратегический R{N}). Это сердцевина стратегической недели: важное системно вытесняется текучкой и ложно-срочным, поэтому защищается осознанно.
   - 🟢 **Текущее (текучка)** — штатная операционная работа, держит конвейер в плановой норме (поддержка, рутина, операционные НЭП).

   **Ось 2 — дедлайн (ортогонально режиму):** есть ли согласованный момент передачи дальше? Дедлайн может стоять на ЛЮБОМ из трёх режимов и сам по себе НЕ делает РП срочным (см. [[Дедлайн ≠ Срочность]]). Помечай дедлайн отдельной меткой `⏰ до DD.MM`, не повышай им режим.

   **Критическая проверка (частая ошибка):** «приближается дедлайн» ≠ «срочное». Сильная неудовлетворённость / высокая мотивация ≠ «срочное» — это важное. Срочное = только физическая угроза остановки конвейера.

3. **Приоритет = функция режима + дедлайн + ТОС.** Порядок взятия в неделю: реальное 🔥срочное (если ещё не закрыто) → 🟡важное под ТОС недели и активные R{N} → 🟡важное с близким ⏰дедлайном → 🟢текучка (минимально необходимая для удержания нормы). Цель недели — защитить квоту 🟡важного, а не дать текучке и ⏰дедлайнам вытеснить развитие.

4. **Свежесть данных и машинное подтверждение (WP-518, 08.09.2026).**

   **Базовый путь — ручной (чистая установка шаблона, скриптов недели нет).**
   Состав пула собираешь ты сам из источников пункта 1 по явно названному
   правилу отбора (приоритет + привязка к активным R{N} месяца). Это твоё
   суждение, а не детерминированный отбор кодом, поэтому:

   - Назови пилоту правило отбора, которым пользовался, и предупреди:
     свободное суждение LLM может расходиться с заявленным правилом
     (найдено 07.09: 6 исключённых РП сами были P1) — состав пула пилот
     проверяет глазами, не полагаясь на формулировку правила.
   - Машинной привязки версии (`content_hash`) и `reason_code` на записи
     при ручной сборке нет. Если пилот спрашивает, почему конкретный РП не
     попал в пул — отвечай честно из своего правила отбора, не сочиняй
     ссылку на несуществующий код отбора.
   - Перед предъявлением пула сам проверь свежесть чекаута governance-репо
     (`git status` / `git fetch`): ручная сборка по устаревшему дереву даёт
     неактуальный пул. Отстал — сначала синхронизируй и пересобери пул.

   **Опциональные ускорители — только если установлены.** Скрипты
   `week-open-scaffold.sh`, `week_pool_manifest.py`, `week-open-llm-fill.py`
   в поставку шаблона не входят (issue #1100) — это оснастка конкретной
   инсталляции. Если черновик пришёл от `week-open-scaffold.sh`, состав
   таблицы уже решён детерминированно кодом (`week_pool_manifest.py`), не
   твоим суждением — и действуют другие правила:

   - Если в шапке секции «План на неделю» есть строка, начинающаяся с
     `⚠️ рабочее дерево` (все 4 варианта баннера — отстаёт / разошлось /
     `git fetch` не удался / нет upstream-ветки — начинаются одинаково,
     проверяй по префиксу, не по конкретной формулировке) — **СТОП**: скажи
     пилоту, что состав пула может быть неактуален, предложи синхронизировать
     чекаут и пересобрать черновик заново. Не продолжай подтверждение на этом
     баннере.
   - Покажи пилоту таблицу пула как есть. Если пилот спрашивает, почему
     конкретный РП не попал в пул — не сочиняй причину: у отбора уже есть
     `reason_code` на каждой записи (создаётся кодом, не тобой); объясни
     значение `cap_exceeded_rank_N_of_M` (не хватило места в shortlist по
     приоритету) как есть, включая честную оговорку — соответствие
     месячному фокусу сегодня НЕ входит в ранжирование (открытый пункт
     РП-518), только приоритет + номер РП.
   - Если состав пула изменился в разговоре (пилот попросил добавить/убрать
     РП вручную) — пул нужно пересобрать заново скриптом, не редактировать
     таблицу от руки: иначе `content_hash` перестанет соответствовать реально
     показанному составу, и шаг 08 упадёт на сверке
     (`strategy-session-checks-runner.sh`, если он установлен — см. шаг 08).

   **Подтверждение пилота — записываемый факт на любом пути, не
   формальность.** После обсуждения дождись ЛИТЕРАЛЬНОГО ответа пилота на
   предъявленный пул (не молчаливого перехода к следующему шагу) и запиши в
   WeekPlan frontmatter `gate_reviews.06a`:
   - `pilot_decision: approved | changes_requested | rejected`
   - `pilot_quote`: короткая дословная цитата ответа пилота
   - `status`: `reviewed` (не `confirmed` — это поле файла целиком, шаг 08)
   Поле `content_hash` существует только на скриптовом пути — оно записано
   автоматически (`week-open-llm-fill.py`), не переписывай его вручную.
