## Принципы

1. **Note-Review НЕ принимает решений** — только классифицирует и предлагает
2. **Предложения пишутся в КОНЕЦ целевых документов** — Стратег (Day-Plan, 4:00) читает их и учитывает
3. **Одобрение человека обязательно** — предложения = рекомендации, не действия
4. **Знание → inbox Экстрактора** — Note-Review не пишет в Pack напрямую
5. **Каждый разбор — запись решения:** заметка покидает `fleeting-notes.md` только вместе с записью в `archive/notes/Notes-Archive.md` вида «**Разбор:** YYYY-MM-DD — **Решение пилота:** …». Архивная запись без решения пилота недопустима (решение владельца шаблона, июль 2026)

## Процесс

#### 1. Прочитать заметки

- Открой `{{GOVERNANCE_REPO}}/inbox/fleeting-notes.md`
- Выдели заметки **жирные без `✅предложено` и без `🔄`** (`**текст**`) — это новые, обрабатывать
- Заметки с `✅предложено` — уже обработаны, не переклассифицировать, оставить как есть
- Заметки с `🔄` — тоже просмотри, но не обрабатывай повторно (если нет нового контекста)
- Если новых заметок нет → сообщить «Новых заметок нет» и завершить

#### 2. Прочитать контекст

- `{{GOVERNANCE_REPO}}/docs/Dissatisfactions.md` — текущие НЭП (S* стратегические, O* операционные)
- `{{GOVERNANCE_REPO}}/current/WeekPlan W*.md` — РП и приоритеты недели
- `{{GOVERNANCE_REPO}}/docs/Strategy.md` — фокусы года, приоритеты месяца
- MEMORY.md — статусы РП
- QA-отчёт бота: `DS-agent-workspace/scheduler/feedback-triage/` (последний по дате) — **структурированный отчёт** из feedback_triage DB (авто-классификация ботом). Замечания (✏️) и urgent (high/critical) — в начале файла. Real-time алерты уже отправлены ботом → Note-Review только проверяет кластеры (≥3 в одном кластере → пометить)

#### 3. Классифицировать каждую заметку

> Восемь категорий (PD.FORM.083). Одна заметка = одна категория (главная).

| # | Категория | Критерий | Куда пишет Note-Review |
|---|-----------|----------|------------------------|
| 1 | **НЭП** | Неудовлетворённость, дискомфорт, «хочу изменить», эмоция | → предложение в конец Dissatisfactions.md |
| 2 | **Задача** | Конкретное действие, «завтра сделать», «нужно проверить», баг/пожелание к любому инструменту | → предложение в конец WeekPlan / DayPlan |
| 3 | **Гипотеза** | Предсказание о мире с проверяемым вердиктом: «если X, то Y», «должно быть верно, что Z». Есть ответ на «что могло бы это опровергнуть?» — иначе это Задача | → черновик 4 полей (утверждение, уверенность %, критерий фальсификации, дата сверки — PD.FORM.083 §3) в конец `current/hypotheses-log.md`. Пилот подтверждает/правит на сверке — Note-Review не формулирует финальную версию сам |
| 4 | **Знание доменное** | Паттерн, различение, метод, правило — применимо вне реализации | → кандидат в DayPlan «Разбор заметок» (с предложением отдать Экстрактору). В `captures.md` — ТОЛЬКО если в заметке явно написано «Экстрактору» / «в captures» / «в Pack» |
| 5 | **Знание реализационное** | Как устроено в конкретной системе, архитектурный выбор | → Задача: задокументировать (WeekPlan) |
| 6 | **Черновик** | Зерно для поста/статьи, рефлексия с концептами | → рекомендация в конец WeekPlan (секция «Предложения Note-Review»). Файл НЕ создаётся — только после согласования |
| 7 | **Личные данные** | Контакт, телефон, email, токен, аккаунт, реквизиты | → {{GOVERNANCE_REPO}}/personal/*.md |
| 8 | **Шум** | Тест, дубль, случайное, ссылка без контекста, уже сделано / решено | → пометка `✅предложено (шум)` (зачёркивает заметку только пилот) |

**Правила классификации:**
- Если НЭП + задача → приоритет НЭП (эмоция важнее действия)
- **Бот-замечание** → поглощено Задачей (категория 2). Отдельной категории нет
- **Идея 🔄** → поглощена Задачей («обдумать X») или Шумом. Пометка 🔄 больше не используется
- **Гипотеза vs Задача:** «обдумать X» без критерия опровержения → Задача, не Гипотеза. Формулировка-предсказание с явным «если… то…» или количественным ожиданием и датой проверки → Гипотеза
- **Черновик vs Знание доменное:** Знание = факт/правило для Pack. Черновик = зерно поста. Одна заметка может породить оба — записать в ОБА места
- Ссылки без контекста → Шум
- **Срочные задачи:** содержит срок («сегодня», «завтра», дату) → Задача с пометкой срока. Если срок = завтра → DayPlan. Если срок = неделя → WeekPlan
- **Личные данные → personal/:** контакт → `personal/contacts.md`, аккаунт/URL → `personal/accounts.md`, токен/пароль → `personal/secrets.md`, прочее → `personal/reference.md`

**Проверка актуальности (обязательно перед классификацией):**
- Сверь заметку с коммитами за сегодня (`git log --since="00:00" --all --oneline` по всем {{WORKSPACE_DIR}}/ репо) и текущим WeekPlan
- Если задача из заметки **уже сделана** (есть коммит или РП done) → Шум (`✅предложено (шум)`), не тянуть в план
- Если проблема из заметки **уже решена** → Шум
- Если заметка ссылается на ситуацию, которая **изменилась** за день → оценить с учётом нового контекста
- Пользователь мог написать утром, а к вечеру всё уже сделал — не создавай лишних предложений
- **Сопоставление с РП (для ВСЕХ категорий):** Перед классификацией любой заметки — проверь по MEMORY.md: совпадает ли intent заметки с существующим РП? Проверяй НЕ только название РП, но и описание результатов (✅ строки). Пример: заметка «Сделать стандарт описания роли» покрыта РП #N (DP.D.033 Role-Centric Architecture) — даже если РП in_progress, конкретный результат done. Если покрыто → Шум (`✅предложено (шум)`, причину «Реализовано: РП #N, артефакт» указать в скобках пометки и в отчёте шага 9). Правило: **заметка, чей intent уже реализован = Шум, независимо от статуса РП**
- **Личные задачи:** Заметки с конкретным действием и сроком (в т.ч. личные, бытовые, семейные) → категория **Задача**. Записывать в WeekPlan с дедлайном. НЕ отбрасывать как «нерелевантные». Недельный план включает ВСЕ задачи: рабочие + личные. Нумерация личных: Л1, Л2, ...

#### 5a. Черновик записи в журнал гипотез (категория «Гипотеза»)

- **Утверждение:** [проверяемое предсказание из заметки]
- **Уверенность:** [если пилот указал % — использовать; иначе оставить `[TBD — пилот заполняет]`]
- **Критерий фальсификации:** [черновик — что могло бы опровергнуть; если в заметке нет явного критерия, предложи наиболее вероятный вариант с пометкой «черновик, требует подтверждения»]

> **Без чата — только пометки и предложения (решение владельца шаблона, июль 2026):** запуск из `strategist.sh` выполняет шаги 1-9 и 11, сам ничего не архивирует и не удаляет (после него работает только скрипт-страховка: она убирает заметки без жирного, без `🔄` и без пометки `✅предложено`); планировщик его не вызывает. #### 10. Записать копию в архив — только по решению пилота, в живой сессии (заметка в fleeting-notes.md сама не удаляется)

> **Решение владельца шаблона (июль 2026):** удаление заметки из `fleeting-notes.md` — не решение Note-Review. Заметка с `✅предложено` остаётся в файле каждый день, пока пилот не уберёт её сам. ## Очистка заметок (ручная, по команде пилота)

> **Триггер:** команда «очистить заметки» / «убери эту заметку» от пилота, или пилот сам зачеркнул заметку (`~~Заголовок~~`). Это основной путь физического удаления из `fleeting-notes.md` (кроме шага 10 для заметок, которые пилот зачеркнул сам, и скрипта-страховки `cleanup-processed-notes.py`, который архивирует заметки без жирного, без `🔄` и без пометки `✅предложено`) — автоматика сама не решает, что убрать (решение владельца шаблона, июль 2026).

1. Прочитай `fleeting-notes.md`
2. Найди заметки, которые пилот явно попросил убрать в этой команде, или уже **зачёркнутые** им (`~~Заголовок~~`)
3. Перенеси их в `archive/notes/Notes-Archive.md`:

```markdown
## YYYY-MM-DD — Очистка

Заголовок заметки
<sub>дата, время</sub>
Дополнительный контекст (если был)
**Категория:** НЭП / Задача / Гипотеза / Знание доменное / Знание реализационное / Черновик / Личные данные / Шум
**Разбор:** YYYY-MM-DD — **Решение пилота:** [дословно или кратко; для зачёркнутых — «зачёркнута пилотом»]

---
```

4. Удали перенесённые заметки из `fleeting-notes.md`
5. **Жирные** (`**текст**`), заметки с пометкой `✅предложено` (жирные или нет) и `🔄` — остаются, пока пилот не назвал их явно
6. Закоммить и запушить
